## 三、踩的坑与解决方案

### 坑 1：venv `python` 链接到 Xcode 3.9（昨日遗留再确认）

- 已在昨日修复，今天直接用 `.venv/bin/python` 显式调

### 坑 2：BGE-M3 首次下载 13 分钟

- **现象**：第一次 ingest GB 50180-2018 耗时 960s，其中 embed 阶段独占 ~95%
- **原因**：HuggingFace 拉 2.3GB 模型权重（含 391 个分片）
- **教训**：首次 ingest 必须计算下载时间预算，后续 ingest 模型已缓存到 `~/.cache/huggingface/`

### 坑 3：QdrantClient 析构 ImportError 噪音

- **现象**：Python 退出时 `ImportError: sys.meta_path is None`
- **原因**：qdrant-client 1.18 本地文件模式的析构时序问题
- **影响**：仅日志噪音，**数据已落盘**，不影响功能
- **处理**：暂不修，等切到 Docker 模式自动消失

### 坑 4（P1 隐性 bug）：chunk_id 静默重复导致 23% 数据丢失

- **现象**：4773 chunks 入库 Qdrant 后只剩 3659 points
- **诊断**：
  ```
  CJJT_91-2017.json: 重复 367/602   ← 术语标准，X.0.Y 同号被切多次
  DB_31T_1557-2025.json: 重复 208/449
  GB_55037-2022.json: 重复 204/422
  ...
  ```
- **根因**：`chunk_id = f"{spec_code}#{clause}"`，但表格续表、章节误识别、子项切分等场景会让同 clause 号被切出多个 chunk
- **修复**：`_emit` 检测重复时自动追加 `_d1` `_d2` 后缀
- **教训**：**Qdrant upsert 用同 ID 是静默覆盖**，无 warning，无 error。这是 RAG 系统最危险的 bug 类型之一——指标好看，数据其实丢了。
- **如何被发现**：跑完冒烟后随手对比 `chunks 总数 vs Qdrant.count()`，发现差值才找出来
- **后续防御**：在 ingest 流水线加 assertion `len(chunks) == ingested_count`

### 坑 5：3 部 PDF chunker 完全无法处理

| 文件 | 根因 |
|---|---|
| 建标 109-2008 | 用全角数字 `表４３`，正则 `\d` 不匹配 |
| 建标 192-2018 | OCR 后表号字符错乱 `&(!!` |
| 上海市 15 分钟生活圈 | PDF 字体 cmap 错乱，文本全是乱码 |

- **MVP 决策**：3 部均接受不入库，记入 `docs/design/known_limitations.md`
- **教训**：算法的鲁棒性边界要早暴露、早记录，避免后期排查浪费时间

### 坑 6：文件名前导空格让 domain 解析失败

- **现象**：` JGJ39-2016...`、` 建标 109...` 因开头空格，`startswith(prefix)` 不命中
- **修复**：`resolve_domain` 自动 `strip()`

### 坑 7：不规则文件名解析失败

- **现象**：`上海市"15分钟..."》.pdf` 没有开《引号，`parse_filename` 正则失败
- **修复**：新增 `INGEST_FILENAME_OVERRIDES` 字典手动指定 (spec_code, spec_name)
- 同时 `chunk_pdf` 加 `spec_code_override` / `spec_name_override` 参数支持

## 九、AIPM 视角的本日反思

### 反思 1：**指标好看不等于系统对**

chunk_id 重复 bug 是这两天最警醒的事——表面 Hit Rate@5 = 5/5 完美，背后却丢了 23% 的数据。如果不是随手对比 chunks 总数与 Qdrant.count()，可能要在 W4 评测时才发现。

**给 AIPM 的提醒**：上线前必须做"数据完整性自检"，不能只看效果指标。

### 反思 2：**OCR 多样性是数据工程的"隐性税"**

42 部规范里有 3 部因为 OCR 异常无法用通用 chunker 处理。这种"边角格式"在真实世界中比想象的多，**AIPM 在数据收集阶段就该评估**：
- 数据源是否已 OCR？
- OCR 质量是否均匀？
- 是否有特殊字符/字体/编码？

提前问这些问题，能让团队在数据准备阶段就剔除/重做问题样本。

### 反思 3：**MVP 阶段的"接受不入库"是合理决策**

3 部未入库的 PDF，单独修要 1-2 天工作量；它们对核心查询能力影响 < 5%。
**AIPM 必须能判断"这值不值得花时间"**——80/20 原则，把时间留给主路径上的瓶颈。

记入 `known_limitations.md`，让决策可审计、可回顾，是负责任的做法。
