## 二、改动 1 · pipeline 集成 strip + emit revised_answer

**文件**：`backend/app/rag/pipeline.py`

流式 token yield 完后：
1. 拼接完整 answer
2. 调 `strip_supplementary_sections()` 净化
3. emit `metadata` 事件（含 `post_filter_stripped_chars` / `post_filter_applied`）
4. 如有剥离，emit `revised_answer` 事件（前端覆盖 / 评测优先消费）

后端 `api/chat.py` 是泛化 `evt["type"]` 透传，自动 forward 给前端。

## 六、12 条真顽疾（4 次评测都触发）分类 — 主矛盾切换

| 维度 | 数量 | 典型 QID |
|---|---|---|
| **dim4 用词错** | **8 条（主矛盾）** | Q077 "宜→应" / Q109 / Q115 / Q117 / Q125 / Q131 / Q139 / Q142 |
| dim5 数字错 | 5 条 | Q003 数字误抄 / Q079 单位缺平方 / Q102 / Q125 / Q131 |
| dim7 主答案编造 | 5 条 | Q003 笔误解释 / Q079 / Q115 / Q117 / Q125 / Q140 |

**主矛盾切换**：W5 dim7 顽疾（编造）已治理（post_filter 起作用），**新顽疾是 dim4 用词错**。

LLM 把"宜""应""不应"等量化词当**同义词**，倾向标准化为"应"——这是更深层的训练惯性，**post_filter 不能治**。

需要 W6 D3+：
- **prompt 加 few-shot 反例**：明示 "宜 ≠ 应" "不应 ≠ 不得超过"
- 或后处理改用 **diff-style 校对**（生成后跟 chunks 比对用词差异）
- 或 chunks 错字二轮（部分 dim4 错可能是 chunks 本身错字）

## 九、AIPM 启示候选

### 启示 55 候选 · post_filter 是 dim7 编造的工程化解药（直接证实启示 52）

W6 D2 实证：
- D6 → D7 唯一变量 = post_filter（剥离"补充说明"节）
- dim7 +11.2pp（71.6% → 82.8%）
- 综合 +1.6 / veto -8

**等价表述**：
- 启示 52 提出"补充说明"是 LLM 训练惯性，需后处理而非 prompt
- W6 D2 用 strip_supplementary_sections + revised_answer 集成直接验证 → **启示 52 成立**
- 这是评测驱动开发（EDD）9 步闭环的完整闭环示范

### 启示 56 候选 · 顽疾主矛盾会随治理进度切换

W5 D3 元评测：dim7 编造主矛盾（78.4%）
W6 D2 post_filter 治后：dim7 已 82.8%，**主矛盾切换到 dim4 用词**

**等价表述**：RAG 系统的质量治理不是"一锅烩"，每个治理阶段的**头号 bug 在变化**：
- 阶段 1：检索召回（W2-W3）
- 阶段 2：编造（W5-W6 D2）
- 阶段 3：用词错（W6 D3+ 主战场）

应用：项目验收不是"达到某个阈值就 GREEN"，而是**持续识别 + 治理新主矛盾**。

### 启示 57 候选 · 集成路径 A1 的"流式 → 覆盖"是干净的 UX 模式

W6 D2 选择 A1（emit revised_answer + 前端覆盖）：
- 用户看到的体验：流式打字 → 末尾轻微"刷新"（剥离的内容消失）
- 评测看到的 answer：净化版 revised_answer
- pipeline 内部：原 answer 保留为 rawContent 供 debug

**等价表述**：流式 + 后处理矛盾不必互斥 — emit 两个事件（原流 + 覆盖事件），各取所需。
