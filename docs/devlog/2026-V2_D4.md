## 一、需求与定位

规范随时间更新、老的会废止。"像查法条"的产品**必须显示现行状态**——把已废止的标成"现行"比不显示更危险（误导用户用废止条款，碰 RED LINE）。PRD E.4 早预留"作废规范"兜底，CSS status token 也早就位，但**徽章一直硬编码"现行有效"**。

## 二、设计（经确认）

- **默认现行 + 例外表**：89 部入库时即现行版本 → 默认"现行"；仅登记非现行的【例外】。
- **🔴 状态不臆断**：已废止/局部废止必须来自权威公告，**绝不编造**。宁可标默认"现行"也不瞎标"已废止"。例外表**初始为空**，待按公告逐步补录（机制先行，权威数据后填）。
- **规范级 · 4 态**：现行 / 已废止 / 局部废止 / 即将实施。

## 五、🎓 启示 75 · 占位 UI 常把"暂时省略"硬编码成"虚假的非此即彼"，加真数据时要先拆 ⭐

CitationCard 原徽章逻辑是 `is_mandatory ? "强制性" : "现行有效"`——一个 XOR：**强制性条文永远不显示现行状态**。这是占位期"反正都现行、先共用一个槽"的省事写法，却悄悄编码了一个假命题（强制 ⊻ 现行）。加真状态时必须先把这俩**正交维度**拆开（强制性=条文属性，状态=现行性），否则强制条文永远显示不出"已废止"。

**对 AIPM 转行的启示**：
- **占位/硬编码常埋假设**：写死的 UALU（"现行有效"）、共用的槽位，往往隐含"这两件事互斥/不重要"的判断。接真数据前先审：这个占位把什么**正交的东西**揉一起了？
- **状态类信息默认值要 fail-safe**：默认"现行"（保守、入库即真）+ 例外登记，绝不让系统**臆断权威状态**（宁可少标也不错标）。与红线 1「不编造」同源——编造"已废止"和编造规范号一样危险。
- **机制先行、权威数据后填**：例外表 ship 时为空，先把"能标、怎么标、标了怎么显示"跑通，真实废止数据按公告逐步补——不为"没数据"卡住功能，也不为"快上线"编假数据。
