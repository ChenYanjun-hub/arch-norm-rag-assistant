# W7 · Agent 能力可见化（前端呈现）— 启示 85

**结论**：⭐ 把三个 agent 的能力做成 UI 可见：分解展示**拆出的子问题**、工具显示**调了哪个工具**、
核验显示**核验通过 / 待核项**。上线实测时 **verifier 当场抓到一个真实的红线级错误**——
LLM 把原文「**不应**把裸灯设置在视平线上」写成「**应把**」，语义完全反转，而规则式 `align_modal_verbs` 漏掉了。
沉淀 **启示 85**（可见化不只是 UI，是让 AI 的不确定性变成可审计的证据）。

---

## 一、动机

三个 agent（查询分解 / 引用核验 / 工具调用）都已生产化，但**用户完全看不见**——
答案里没有任何痕迹说明"这题被拆成了 4 问""这题是工具查的""引用已核验"。
对规范问答这种"要可追溯"的产品，agent 的工作过程本身就是可信度的一部分。

## 二、实现

后端补一个字段（`retrieval` 事件加 `sub_queries`），前端做三层呈现：

| Agent | 头部徽章 | 卡片内详情 |
|---|---|---|
| ① 查询分解 | `⑂ 已拆解 4 问` | 蓝色条：逐条列出拆出的子问题 |
| ② 引用核验 | `✓ 引用已核验` / `⚑ N 处待核` | 琥珀条：逐条列出无据项 + 原因 |
| ③ 工具调用 | `⚒ 工具 list_specs` | —（工具答案本身即结果）|

- `types/chat.ts`：`RetrievalMeta` +`decomposed`/`sub_queries`；`PipelineMeta` +`grounding_*`/`tool_agent_*`。
  同时把 `dangling_count` 等三项改为可选——**工具路径不检索，本来就不下发这些字段**（类型要说实话）。
- `ChatMessage.tsx`：徽章 + 子问题条 + 核验告警条；`design.css`：`.cn-agent-*` 样式。

## 三、🎯 上线实测：verifier 抓到真实红线违规

用「城市新区的道路建设有什么规范要求？」实测，UI 正常显示 4 个子问题，
**同时核验条弹出一处待核**：

> ⚑ 引用核验发现待核项
> 居住区人行道路照明灯具安装高度不宜低于3.5m，**应把裸灯设置在视平线上** ——
> 片段[6]原文为"**不应**把裸灯设置在视平线上"，答案写为"应把"，与原文强制性用语不符

**这是真实的红线 3 违规**（强制性条文用语不可错）：LLM 漏了一个"不"，把禁止性规定说成了要求性规定，
**语义完全反转**。而规则式 `align_modal_verbs` 没抓到它（上下文锚点匹配未命中这种跨字的否定词丢失）。

**这是启示 83「规则 + LLM 核验分工」最好的实战证据**——不是理论推演，是上线第一条 query 就抓到了。

## 四、🎓 启示 85 · 可见化是把不确定性变成可审计的证据 ⭐

**AI 产品的"过程可见"不是装饰，是信任基础设施。**
同一个答案，带上"已拆解 4 问 / 引用已核验 / 工具 list_specs"的痕迹，和不带，
用户对它的信任程度完全不同——因为他能**看见系统做了什么、以及系统对自己的怀疑**。

**对 AIPM 转行的启示**：
- **把 agent 的中间过程暴露出来，等于给用户一个审计入口**。尤其"⚑ N 处待核"——
  产品**主动承认"这里我不确定"**，比假装完美更可信，也更符合"像查法条"的严谨定位。
- **可见化会反向暴露问题**：这次 UI 一上线就把 verifier 抓到的红线违规摆到了台面上——
  如果只存在 metadata 里，没人会发现。**观测性做在 UI 上，bug 才会被看见。**
- 顺带修了个可见化才发现的老 bug：前端引用角标正则 `\[(\d+)\]` 会把
  「建标**[2015]**273号」的年号渲染成可点引用（后端 W5 D5 已收紧为 1-2 位，前端漏改）→ 已对齐。
