## 二、5 轮诊断（每轮都被数据修正）

### 轮次 1 · OCR 编号污染

抽样看 GB 50180-2018 第 14 页的 PyMuPDF `.get_text()` 输出：

```
原 PDF 文本层抓出来：
"…应符合表415的规定。表40.3 低层或多层高密度居住街坊
用地与建筑控制指标…住名建筑…探地率…"
                ↑↑↑↑↑      ↑↑     ↑↑↑
             应是「4.1.5」 「住宅」 「绿地率」
```

**第一波结论**：PDF 文件名带 "_可搜索"，是 OCR 加文本层的版本——但 **OCR 本身就烂**。chunker 没做错，错在 PDF 制作时上游 OCR 引擎。

### 轮次 2 · 全库量化错误率

```
chunks 总数: 4773
clause "污染" 总数: 1009（21.1%）
```

21% 看起来很惊人。但拆解：
```
  11x  '1.0.2+1.0.3'   ← chunker 合并策略产物，合理
   9x  '6.4.1+6.4.2'   ← 同上
   ...
```

**>90% 是 `clauseA+clauseB` 合并形态**——这是 chunker 把"短条文 + 表格说明"合并，不是 OCR 错。

真正 OCR 错位（"40.3" 这种两位数 . 一位数）：**全库只有 18 条（0.4%）**。

text 字符级错（"住名/高屋/建统气" 这些 OCR 高频错）：**全库 4 条**。

**结论**：OCR 不是主要瓶颈。

### 轮次 3 · 评测集与库的精确对账

写脚本对 v2 评测集 38 条逐条核查：

```
v2 评测集 38 条 strict 命中分布：
  ✅ chunks 里能 grep 到 expected_clause: 8
  ❌ chunks 里压根没有 expected_clause:   14
  ⚠️ expected_spec 不在库:                16
```

但 8 条 grep-able 的，run_eval 只命中 1 条（strict Hit@5 = 1/38 = 2.6%）。**剩下 7 条 chunks 有这个 clause，但 run_eval 报 miss**——意味着这些 chunks 没进 top-K！

### 轮次 4 · 看真实召回 top-20

抽 4 条 grep-able 但 miss 的 query 看完整 top-20：

```
Q010 "办公建筑的耐火等级最低要求？" 期望 GB 55037-2022 5.1.3
[ 1] 0.705 GB 55037-2022 5.3.1   ← "耐火等级" 但 5.3 章
[ 2] 0.705 GB 55037-2022 5.3.1   ← 同 score 重复
[ 3] 0.704 GB 55037-2022 5.3.2
[ 4] 0.704 GB 55037-2022 5.3.2   ← 重复
[ 5] 0.703 GB 55037-2022 5.2.1
[ 6] 0.703 GB 55037-2022 5.2.1   ← 重复
...
[11] 0.653 GB 55037-2022 5.1.1   ← 5.1 章节才出现！
```

**两个独立问题**：
1. **top-20 里每条 chunk 连续出现 2 次**（rank 1+2 同 score / 3+4 同 score）
2. **BGE-M3 把 5.3 防火等级条款打分高于 5.1 耐火分类**——expected 5.1.3 直到 rank 11 才出现

### 轮次 5 · 重复假设核实

立刻怀疑数据库重复入库：

```
Qdrant 总点数: 4773
JSON 总条数:   4773    ← 1:1 完美对齐
按规范分布也完全一致
```

**没有重复入库**。

那连续出现 2 次怎么解释？看 GB 55037-2022 的 chunks JSON：

```
422 chunks / 228 独立 clause = 1.85 倍重复率
clause='5.1.2+5.1.3' 出现 2 次：
  chunk_id=GB 55037-2022#5.1.2     text="5.1.2\n建筑高度大于100m..."
  chunk_id=GB 55037-2022#5.1.2_d1  text=完全相同
```

**真正问题**：chunker.py `_emit` 函数的 `_dN` 后缀机制（W1 时为防 "OCR 错位/章节误识别让同 clause 号被切多次"加的）**chunk_id 唯一了，但内容没去重**。

这就是 W1 Day 2 task #22 "修复 chunk_id 重复" 修了一半的债：id 唯一 ✅，text 唯一 ❌。

## 三、做了什么 · retriever 层 dedup

### 设计

不动 search() 接口，新增独立 dedup 函数：

```python
# backend/app/rag/retriever.py
def _norm_text_for_dedup(text: str, prefix_len: int = 200) -> str:
    return "".join((text or "").split())[:prefix_len]

def dedup_results(results, *, prefix_len: int = 200):
    seen = set()
    kept = []
    for r in results:
        p = r.get("payload") or {}
        key = (p.get("spec_code", ""), _norm_text_for_dedup(p.get("text", "")))
        if key not in seen:
            seen.add(key)
            kept.append(r)
    return kept
```

### 接入

```python
# pipeline.py：search 后 dedup，粗排放大 2× 补偿损耗
raw_results = search(qvec, top_k=top_k_rough * 2)
raw_results = dedup_results(raw_results)[:top_k_rough]
```

```python
# run_eval.py：加 --no-dedup flag 方便对照
parser.add_argument("--no-dedup", action="store_true")
```

### 数字对照

| 指标 | dedup OFF | dedup ON | Δ |
|---|---|---|---|
| Hit@5 strict | 2.6% | 2.6% | 0 |
| Hit@5 loose | 47.4% | 47.4% | 0 |
| **Hit@10 strict** | **2.6%** | **5.3%** | **+2.6pp** ⭐ |
| Hit@10 loose | 52.6% | 52.6% | 0 |
| MRR strict | 0.026 | 0.030 | +0.004 |

**意外结论**：dedup 让 top-10 strict **翻倍**，但 top-5 没动。

为什么？reranker 已经在做语义筛选，dedup 在 reranker 之前只是把候选池变得更多样化——但 reranker 之后的 top-5 排序仍然是按语义打分，dedup 贡献被 rerank 吸收了。

## 四、推翻一切先验后的真正瓶颈

| 假设 | 实测占比 | 是否主因 |
|---|---|---|
| ❌ OCR 字符错 | < 0.1%（4 条）| 不是 |
| ❌ OCR 编号乱 | < 0.5%（18 条）| 不是 |
| ❌ 向量库重复入库 | 0 | 不存在 |
| 🟡 chunker text 重复 | 1.85 倍率 | 仅影响 top-10 |
| ⭐ **BGE-M3 语义召回偏** | **Q009/Q010 期望 5.1 全 miss** | **真正主因** |

**Q009/Q010 暴露的核心问题**：
- "办公建筑的耐火等级" 在 BGE-M3 看来更接近 "5.3 防火等级" 而非 "5.1 耐火分类"
- "高层民用建筑分类标准" 召回到的全是 5.2/5.3，5.1 章节零召回
- 这是 embedding 模型在**专业术语近义但章节归属不同**场景的固有弱项

**40+ pp 的提升空间在这里**，不在 OCR 也不在 dedup。

## 六、AIPM 启示（今晚收获）

### 启示 14 · 诊断要诚实，不要"假设驱动开发"

最初确信"strict 这么低肯定是 OCR"——如果不停下来做 5 轮诊断，今晚就直接开始装 PaddleOCR/Marker 重 ingest，**3 小时后发现解决不了问题**。

诊断纪律：
1. **不下结论前先量化**（不仅看错例，要全库统计）
2. **每个假设都要能被数字证伪**
3. **当数字与直觉冲突时，相信数字**

### 启示 15 · "改了不涨"也是成果

dedup 改完 Hit@5 没动，看起来"白干"。但：
1. 排除了一个潜在主因（**节约后续 3-4 小时**诊断时间）
2. top-10 strict 真实 +2.6pp
3. 为后续 query 改写 / hybrid 提供干净的基础设施（不会再被 _dN 噪声污染）

**AIPM 视角**：评测体系最大的价值不是"算涨了多少"，而是 **"算出哪些动作没用"**——后者帮你停止浪费时间。

### 启示 16 · 召回与精度是两条独立赛道

47.4% loose vs 2.6% strict 的巨大裂口告诉我：
- **召回层先做对**（找对 spec_code）
- **精度层才有意义**（找对 clause）

如果一开始就盯 strict 数字优化，等于在召回还没及格时跑去刷精度——属于在错的层级花力气。
