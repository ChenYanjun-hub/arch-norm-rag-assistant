### D2（周一 / 2026-06-01）· 评测集修复 38 → 50 有效 [3h]

🎯 **目标**：把 v2 评测集 50 条里的"边角废条"（spec 不在库的 16 条）修成"可评测"

📋 **步骤**：

1. **诊断**（30min）：
   - 用 `inventory_diff` 思路扫一遍 v2 集
   - 列出 16 条 "expected_spec 不在库" 的明细
   - 对每条决定处置：
     - **路径 A**：改 expected_spec 为入库的相似规范（如 DB11/1224-2023 北京地标 → GB 50180-2018 国标）
     - **路径 B**：保留作为"无答案"测试（验证 fallback）

2. **修复**（1.5h）：
   - 写 `backend/scripts/build_eval_v3.py`（沿用 v2 build 思路）
   - 逐条修订或重设 expected_spec / expected_clause
   - 人工核对 chunks 里是否真有对应条文

3. **冒烟评测**（30min）：
   - 跑 v3 集（仍 50 条但更多有效）
   - 看 hit@5 loose 是否能从 50.0% 提升到 60%+

4. **commit + push**（30min）

📝 **验收**：
- v3 评测集 50 条，**有效条目（expected_spec 在库）≥ 45 条**
- v3 集跑 baseline 的 Hit@5 loose **≥ 55%**（v2 是 50%，v3 含修复条目应该涨）

⚠️ **风险**：
- DB11 北京地标真不在库 → 只能改为"国标对照测试"
- 改 expected 可能引入主观偏差 → 每条都要核对原文

### D3（周二 / 2026-06-02）· 评测集扩 50 → 100 总量 [4h]

🎯 **目标**：补 50 条新场景，覆盖 W3 D5 新加的 8 类 fallback + 更多规范域

📋 **步骤**：

1. **新增 query 分布设计**（30min）：

| 类别 | 数量 | 来源 |
|---|---|---|
| 规划深化 | 6 | GB 50180-2018 / CJJ 91-2017 多条文 |
| 建筑深化 | 8 | GB 50096-2011 / JGJ 39-2016 / GB 55031-2022 |
| 消防深化 | 8 | GB 55037-2022（重点）+ GB/T 39972-2021 |
| 景观新增 | 6 | CJJ 91-2017 / 地方标多条 |
| 8 类 fallback × 各 3 条 | 24 | 每类典型 query 验证识别准确 |
| **合计** | **52** | （目标 50，多 2 留余）|

2. **自动生成草稿**（1h）：
   - 写 `backend/scripts/gen_eval_v4_draft.py`：扫入库 chunks 的 clauses，按域+难度生成 query 草稿
   - 草稿格式同 v3 CSV
   - 标记每条的目标 expected_spec / expected_clause

3. **人工核对 + 微调**（1.5h）：
   - 逐条审 50 条新 query 的合理性（防止 LLM 凭空编造）
   - 每条 expected_clause 必须能在 chunks JSON 里 grep 到
   - 多样化提问方式（含正问 / 反问 / 数值型 / 概念型）

4. **冒烟评测**（30min）：跑 v4 集 100 条看 baseline 数字

5. **commit + push**（30min）

📝 **验收**：
- v4 评测集 **100 条**（v3 50 + 新 50）
- 8 类 fallback 各 ≥ 3 条覆盖
- 5 类规范域均衡（每域 ≥ 15 条）
- 跑评测，**Hit@5 loose ≥ 50%**（不必涨，但能验证扩量后数字稳定）

⚠️ **风险**：
- 50 条全靠人工核对耗时长 → 用 LLM 草稿 + 重点抽查
- 引入偏向自己 RAG 的 query → 故意混入"我也不知道答案"的 query 测真实 case

### D4（周三 / 2026-06-03）· 跑 100 条评测 + 多维度报告 [2h]

🎯 **目标**：用 v4 100 条产出可对外展示的真实评测报告

📋 **步骤**：

1. **跑 4 组合**（30min，并发受 Qdrant 锁限制只能顺跑）：
   - baseline (mq=off, hybrid=off)
   - mq=on（W3 D2 主力配置）
   - mq=on + dedup ck=30（W3 D4 失败的）
   - mq=on + hybrid=on（W3 D3 失败的）
   - 重新评估 4 组合在 100 条上的表现

2. **写报告**（1h）：`docs/eval/2026-W4_eval_v4_100q_report.md`
   - 总体 4 组合对比表
   - 按域 / 难度 / 难度类型拆分
   - 错例 top 20 分析
   - 与 W3 D2/D3/D4 数字对比，看是否仍成立

3. **跑监督**（20min）：
   - 100 条 query 中是否出现 W3 没见过的失败模式？
   - 错例集中度更高还是更分散？

4. **commit + push**（10min）

📝 **验收**：
- v4 100 条评测报告 .md（含数字 + 错例 + 跨配置对比）
- W3 结论是否在 100 条上仍成立的"复测"结论

## 🎓 W4 心态

W3 学到"接受技术天花板"。W4 要学到 **"接受数据建设是慢工"**。

评测集不像代码——它没有"跑通 / 没跑通"的二元判断。每条 query 的好坏需要人工审核。**慢慢做，但要做对**。

> **W4 真正的成果不是"评测数字涨了"，是"评测数字能被信任"。**
