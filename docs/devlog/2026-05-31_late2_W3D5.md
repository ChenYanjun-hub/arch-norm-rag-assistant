## 二、做了什么

### 1. `scenario.py` 升级 8 类识别 + 优先级链

```
ScenarioType = Literal[
    "input_empty",     # 1. 空字符串
    "input_too_long",  # 2. > 500 字符
    "sensitive",       # 3. 规避审查 / 绕过审批
    "deprecated",      # 4. 涉及已废止规范号
    "chitchat",        # 5. 闲聊
    "out_of_scope",    # 6. 超范围
    "ambiguous",       # 7. 模糊提问
    "normal",          # 8. 进入正常 RAG 流程
]
```

**优先级序设计要点**：
- **sensitive 排第 3**（仅次于输入校验）—— 一旦命中敏感词，立刻拦截，**绝不让它走 RAG 调 LLM**（CLAUDE.md 红线 4）
- **deprecated 排 sensitive 后**—— 涉及废止规范是事实问题，需要硬编码映射，比 sensitive 更具体
- **ambiguous 排最后**—— 判定最弱（基于长度+关键词），容易误判，必须前面所有类都排除后才考虑

### 2. 关键词集设计（宁错漏不错杀）

#### Sensitive 正则（15 条 pattern）
```python
"如何.{0,4}规避", "怎么.{0,4}规避", "如何.{0,4}绕过", "怎么.{0,4}绕过",
"不被.{0,4}审查", "不被.{0,4}发现", "绕(过|开).{0,5}(审|检|查)",
"违规.{0,4}(怎么|如何)", "偷.{0,3}做", "藏.{0,3}起来",
"瞒.{0,3}过", "假报.{0,3}", "虚报.{0,3}", "少算.{0,3}", "怎么.{0,5}过审",
```

#### Deprecated 硬编码映射（6 个高频废止号）
| 废止号 | 现行替代 |
|---|---|
| GB 50180-93 / -2002 | GB 50180-2018 |
| GB 50016-2006 | GB 50016-2014 / GB 55037-2022 |
| GB 50096-1999 | GB 50096-2011 / GB 55037-2022 |
| JGJ 39-87 | JGJ 39-2016 |
| GBJ 16-87 | GB 50016-2014 / GB 55037-2022 |

#### Ambiguous 三段长度判定

| 长度 | 判定 |
|---|---|
| < 4 字 | 必模糊（"GB"、"规范"、"高度"） |
| 4-15 字 | 必须 ≥ 1 个具体名词 + （问号词 或 ≥ 2 个名词）|
| > 15 字 | 默认 normal |

具体名词集 28 个（设计对象 + 参数）；问号词集 15 个（疑问代词 + "要求/标准/规定"）。

### 3. `fallback.py` 加 5 套兜底文案

| 文案 | 长度 | 设计要点 |
|---|---|---|
| `FALLBACK_INPUT_EMPTY` | 75 字 | 直接给 2 个示例 query 启发提问 |
| `FALLBACK_INPUT_TOO_LONG` | 115 字 | 教用户"拆分提问"方法论 |
| `FALLBACK_SENSITIVE` | 155 字 | **3 类合规咨询渠道** + 强调"原文查询，不提供规避方案" |
| `FALLBACK_AMBIGUOUS` | 130 字 | **3 维补充信息** + 示例 query |
| `build_fallback_deprecated(code)` | 动态 | 废止号 → 现行号 + 名称 + 年份 |

**红线遵守**：所有兜底文案**预设字符串**，绝不调 LLM 生成（CLAUDE.md 红线 4：避免 LLM 自由发挥越界给"规避建议"）。

### 4. `pipeline.py` 8 类全接入

```python
scenario = detect_scenario(raw_query)
if scenario != "normal":
    # 按 scenario 选 fallback 文案 + yield token 流 + done
    return
```

`INPUT_EMPTY` / `INPUT_TOO_LONG` 从原来的 `error` event 改成 `fallback` event + 文本流——**前端体验从"红色报错"变成"友好提示"**。

## 四、AIPM 启示（W3 D5 收获）

### 启示 29 · "礼貌拒答" 是 AI 产品的核心能力

很多 AI 产品犯的错：**所有问题都瞎答**。
- 用户问"如何规避审查" → AI 给出 5 步规避方案
- 用户问"GB 50180-93 怎么算容积率" → AI 编个 2024 修订版的算法

**真正成熟的产品有清晰的边界感**：
- 能力边界（"超范围 → 引导"）
- 合规边界（"敏感 → 拒答 + 引导咨询主管部门"）
- 时效边界（"废止 → 提示现行版本"）
- 信息边界（"模糊 → 主动追问"）

这 4 类边界让产品**值得信任**——"AI 法条数据库"的定位才能真正立住。

### 启示 30 · 优先级链是兜底设计的核心

8 类全覆盖最难的不是"识别每一类"，而是**当一个 query 同时匹配多类时怎么选**。

例：query = "GB 50180-93 怎么规避审查？"
- 命中 `deprecated`（含废止号）
- 命中 `sensitive`（含"规避审查"）

**应该走哪个**？

W3 D5 设计：**sensitive > deprecated** —— 用户意图核心是"规避"，先拒答规避，再提废止反而是次要信息。

类似地，整个优先级链：
```
input_invalid → sensitive → deprecated → chitchat → out_of_scope → ambiguous → normal
```

每个相邻位置的选择都是 **产品价值观的体现**。

### 启示 31 · 分段判定 > 单一阈值

W3 D5 ambiguous 判定从"硬阈值 < 8 字"改成**三段**：
- < 4 字：必模糊
- 4-15 字：关键词组合判断
- > 15 字：默认放行

**单一阈值的陷阱**：永远会有 1 个边界 case 让你纠结调高调低。
**分段判定**让每段有自己的逻辑，避免"为救一个 case 调阈值反而打破另一个 case"。

### 启示 32 · TODO 不只是注释，是技术债的可见性

W2 D1 留的 TODO 在 W3 D5 完成。如果当时没在 scenario.py 写明 `⏸ ambiguous (TODO W3)`，今天大概率会忘记补这 3 类。

**TODO 写得好的标准**：
1. 标明属于哪个迭代（W3、W4 等）
2. 写明为什么没做（"简版先跑通"）
3. 写明应该怎么做（具体的关键词 / 文案方向）

**工程债的可见性 = 长期演进的纪律。**
