# W7 · 项目工作区 — 启示 89

**结论**：⭐ 对齐原型的信息架构核心。关键设计判断：**项目不只是"会话文件夹"，更是"预设的规范范围"**——
同一个问题在深圳和在哈尔滨，适用的地标与气候区参数不同。
这让项目接上了已有的 `spec_code` 多选检索能力，从"分组标签"变成"工作流上下文"。
沉淀 **启示 89**（把新功能接到已有能力上，而不是并排再造一个）。

---

## 一、产品定义（先想清楚"项目是什么"再写代码）

原型左栏有「项目工作区」（深圳前海T3地块 24 / 杭州未来社区试点 12 …）。
如果只做成"会话分组"，那它就是个文件夹，价值有限。真实工作流里，规划师的痛点是：

> 同一个"日照间距怎么算"，在深圳要叠深标 + IV 气候区系数，在哈尔滨完全是另一套。

所以定义为：**项目 = 会话分组 + 预设规范范围**。后者直接复用已有的多选 `spec_code` 检索过滤
（NAV/MULTI 阶段做的能力），无需新增任何后端接口。

## 二、实现

| 层 | 改动 |
|---|---|
| 类型 | `Project{id,name,city?,specCodes[],createdAt}`；`Conversation.projectId?` |
| Store | `projects` / `activeProjectId` + 建/删/选/设范围四个 action，localStorage 持久化 |
| Sidebar | 「项目工作区」区块：建项目、选中（左侧竖条）、会话计数、⛬预设数、存范围、删除 |
| Chat | 顶栏项目标签；新会话继承当前项目 |
| 检索 | 项目预设自动注入 `spec_codes` |

**三条设计取舍（都是为了不夺走用户控制权）**：
1. **手动限定优先于项目预设** —— 用户在侧栏选了规范就用他选的，没选才用项目预设。
   否则会出现"我取消了限定却取消不掉"。
2. **删项目不删会话** —— 只解除归属。用户的问答历史比分组更宝贵。
3. **选中项目=进入该项目上下文** —— 历史列表只显示该项目会话，标题变「本项目会话」。

## 三、🎯 实测发现的两个 bug（都不是靠读代码发现的）

### bug 1：TypeScript 抓到的"删会话会抹掉所有项目"
`deleteConversation` 里是 `savePersisted({ conversations, activeId })`——传的是**局部对象**。
加了 `projects` 字段后，这行会把项目整个写没。**编译器直接报错拦下**，改为 `savePersisted(get())`。
> 这类"局部对象当完整状态存"的坑，正是类型系统的价值所在。

### bug 2：浏览器实测抓到的"在新项目里提问，却续到了项目外的旧会话"
`createProject` 自动选中了新项目，但**没清 `activeId`**，于是提问续在了上一个会话里，
会话没归入项目、顶栏也不显示项目标签。
`selectProject` 有清 `activeId`，`createProject` 漏了——**两个入口行为不一致**。
修复后复测通过。

> 真实用户键盘输入走的就是原生事件路径（已用原生事件验证通过）。

## 五、🎓 启示 89 · 把新功能接到已有能力上，而不是并排再造 ⭐

「项目工作区」如果只做成分组，就是又一个孤立功能。把它定义成**预设规范范围**之后，
它直接复用了早先做的 `spec_code` 多选过滤——**零后端改动，却让两个功能互相放大**：
多选过滤有了"记忆"，项目有了"实质作用"。

**对 AIPM 转行的启示**：
- 做新功能前先问：**"我现有的哪个能力，正缺一个使用场景？"** 很多时候新需求的最佳实现，
  是给旧能力加一个入口，而不是从零造一套。
- **判断一个功能是不是"真功能"，看它有没有改变系统行为**。分组只改变视图；
  预设规范范围改变了**检索行为**——后者才值得做。
- 两个 bug 分别被**类型系统**和**浏览器实测**抓到，读代码都不会发现：
  静态检查和动态验证抓的是不同类的错，**都不能省**。
