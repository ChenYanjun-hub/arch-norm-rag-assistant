## 四、灾难根因（核心诊断）

### 表象：单 case 测试 work

实际单 case 测试：
```python
chunks = ['居住区绿地率宜大于 35%。', '人均面积不应小于 1.0m²/人。']
answer = '居住区绿地率宜大于 30%。人均面积不应小于 1.5m²/人。'
→ aligned = '居住区绿地率宜大于 35%。人均面积不应小于 1.0m²/人。' ✅
```

算法本身能正确改 LLM 错数字。

### 根因：chunks 多数字 + anchor 误匹配

实际 RAG 跑批时：
- chunks 一般 5 条（reranker top-5）
- 每条 chunks 含多个数字
- **同类条文不同数值经常并存**（如 "5 班幼儿园" 和 "12 班幼儿园" 在同一 chunks）

当 LLM 给的数字本来是对的（来自 chunks A），align 可能匹配到 chunks B 的数字 anchor 强行替换。

### 例子：Q002 五分钟生活圈

- chunks 含"五分钟生活圈"+"十五分钟生活圈"两类
- LLM 答案数字本来对应"五分钟"
- align 可能误匹配"十五分钟"的数字 anchor 强行改

### 关键不对称 — 量词 vs 数字

| 维度 | 量词（W6 D4 align）| 数字（W7 D1 align）|
|---|---|---|
| 类别集合 | **9 个**（应/不应/宜/不宜/...）| **无穷**（每条规范几十个数字）|
| chunks 里频次 | 每条 chunks 1-3 个量词 | 每条 chunks 5-20 个数字 |
| Anchor 唯一性 | 高（量词上下文窄）| **低（数字上下文密集，容易误匹配）**|
| 误改成本 | 中（用词变化但语义类似）| **高（数字错语义完全不同）**|

→ **align_numbers 的 anchor 误匹配率比 align_modal_verbs 高 5-10 倍**。

## 五、🎓 启示 62 候选 · 后处理矩阵叠加不是无条件 ⭐⭐

W7 D1 失败实验直接挑战 W6 D4 启示 60「后处理矩阵链式叠加合规性」。

### 启示 60 修正

原启示 60："post_filter 工程模式可以无缝叠加，每加一层治一个 LLM 训练惯性"。

**W7 D1 修正版（启示 62）**：

> post_filter 矩阵叠加的**前提条件**：
> 1. 待治维度的"语义实体"在 chunks 中**类别有限 + 上下文窄唯一**
> 2. 误改成本可承受（哪怕错改，语义不会完全反向）
>
> 量词满足两个条件（9 类 + 上下文紧密 + 误改仍接近原意），所以 align_modal_verbs 成功。
> 数字**不满足**（无穷类 + 上下文密集 + 误改语义完全错），所以 align_numbers 失败。

### 等价表述

- "后处理矩阵" 不是无脑流水线，每层都要先验证可叠加性
- 通过条件：在真实 RAG 流（不只是单 case）跑全量 quality_eval，看主目标维度是否真涨
- 不通过：F.2 立即回滚（W7 D1 实证）

### 应用：W7+ 路径修正

❌ **不再做** "_align_numbers 升级版"（如更严 anchor）— 数字的根本性不对称无法工程治理
✅ **可做**：
- chunks 二轮 OCR 校对（启示 49 / W7+ P0）
- 评测扩 250（用户审核 100 新 query）
- chunks_quality_v2 扫错字模式
- Judge prompt v2 防自身 hallucinate（启示 48 落地）
