## 四、踩的坑与解决方案

### 坑 1：Python 3.11 缺失

- **现象**：系统默认 Python 3.9.6，CLAUDE.md 锁定 3.11+
- **处理**：按 CLAUDE.md G.1「修改环境基线必须先问」，停下来问用户
- **解决**：用户 `brew install python@3.11`，得到 3.11.15
- **教训**：环境探测要在项目第一天做，不要假设系统已就绪

### 坑 2：venv 创建后符号链接错乱

- **现象**：`pyvenv.cfg` 显示 3.11.15，但 `.venv/bin/python` 指向 Xcode 的 3.9.6
- **原因**：venv 在不同 Python 版本下重复创建，符号链接未覆盖
- **解决**：`rm -rf .venv` 重建，验证 `.venv/bin/python --version`
- **教训**：venv 重建比修复链接更简单

### 坑 3：chunker 第一次跑出来 0 个 clause、23 个 appendix

- **现象**：PDF 的目录页有「附录 A 技术指标」字样，触发 `RE_APPENDIX_START`，导致后续全部 chunks 被错标 appendix
- **诊断方法**：用 pymupdf 直接读 PDF 各页文本 + 字号信息
- **修复**：附录识别加严，要求字号 ≥ 14pt 且行长 ≤ 30 字（目录里字号 ≈ 10.9pt 被过滤）

### 坑 4：行末没换行的条文号不匹配

- **现象**：PDF 文本里「1.0.3\n城市居住区...」——条文号单独成行
- **原因**：我的正则 `^\s*(\d+\.\d+\.\d+)\s` 要求条文号后跟 `\s`，但 line text 末尾可能没空白
- **修复**：改 `(?:\s|$)` 允许行尾；再加 `(?!\d)` 避免匹配过长

### 坑 5：附录条文用字母编号

- **现象**：附录里是 `A.0.1`、`B.0.1`，主条文正则不识别
- **修复**：新增 `RE_CLAUSE_APPENDIX = r"^\s*([A-Z]\.\d+\.\d+)(?!\d)"`，仅在 `in_appendix=True` 时启用

### 坑 6：OCR 错字让页码"20"被识别为章节

- **现象**：PDF 末尾页码行 "20"（size=16.1，独立成行）被章节正则匹配
- **修复**：章节标题要求至少 2 个中文字 + 4 ≤ len ≤ 25

### 坑 7（最严重）：API key 险些公开泄露

- **现象**：用户首次设环境变量时把 key 粘到了 `.env.example`（模板，会进 git），而不是 `.env`（gitignore 排除）
- **检测时机**：开会前 PR 阶段，session resume hook 提示文件被修改
- **处理**：
  1. 立即写 `.env`（gitignore 排除）保存真 key
  2. `.env.example` 恢复占位符，加「严禁填真 key」警告
  3. 确认历史 commit 干净（之前的 .env.example 只有占位符）
- **教训**：`.env.example` 与 `.env` 的区别要在 README 显眼处说清楚

**已知缺陷**（详见 `docs/design/chunker_smoketest_GB50180.md`）：
1. chapter 字段部分错乱（OCR 错字）→ 不影响 chunk text 和引用
2. 少量条文号 OCR 错位（如 3.0.8→5.0.8）→ 极个别引用号错
3. 5 个 chunk 超 800 字（最长 1087）→ BGE-M3 仍能编码
4. 强制性识别 ~85% 准确率（目标 90%）→ 关键词单一信号上限
