## 三、citations vs search 8pp 差距的真因

**首次量化发现**：

| 工具 | 测量 | loose | strict |
|---|---|---|---|
| run_regression | retriever search 结果（前 5 chunk）| 93.1% | 76.7% |
| run_quality_eval | RAG pipeline 输出的 citations（LLM 选过的）| 84.5% | 67.2% |
| **Δ** | - | **-8.6pp** | **-9.5pp** |

**原因**：LLM 可能只引用 2-3 条 chunk，导致 `citations[:5]` 不足 5 个，loose 命中率自然降低。

**启示**：RAG 评估必须分两层（**检索能不能找到** vs **LLM 能不能用对**），单一指标会误导。

## 四、35 条 veto 触发详情

### 多维触发分布

| 触发组合 | n |
|---|---|
| 仅 dim7（编造）| 13 |
| dim4 + dim7 | 9 |
| 仅 dim4（用词）| 5 |
| dim4 + dim5 | 3 |
| 三项全触 | 2 |
| 仅 dim5（数字）| 2 |
| dim5 + dim7 | 1 |

### 按域

| 域 | n | veto | 触发率 |
|---|---|---|---|
| 消防 | 11 | 0 | **0.0%** ✅ |
| 规划 | 41 | 8 | 19.5% |
| 景观 | 17 | 5 | 29.4% |
| 建筑 | 35 | 16 | **45.7%** ⚠️ |
| 综合 | 12 | 6 | **50.0%** ⚠️ |

**洞察**：建筑设计规范的"配套数据"（照度、人均面积等）容易触发模型联想编造；跨规范综合题让 LLM 从相关知识库"补充"，是编造重灾区。

### 编造模式 4 类（25 条 dim7 = 0 的共性）

1. **编造引用号 [4][5][6]** — 模型为"显得完整"虚构脚标
2. **补充说明区编造内容** — "根据规范/经验补充：..."
3. **编造"强制性条文"标签** — 把非强条说成强条
4. **编造跨规范引用** — 联想到相关规范但 chunks 没给

## 五、抽样 30 条人工核对 — Judge 准确性

**工具**：`scripts/sample_quality_review.py`（W5 D3 新建）
**抽样**：15 条 veto + 15 条 non-veto = 30 条
**输出**：`data/eval/quality/sample_review_20260603_134410.md`（1219 行）

### Judge 准确性汇总

| 类型 | 30 条占比 |
|---|---|
| 完全正确 | 18 / 30 = **60.0%** |
| 错判（Judge 自己 hallucinate 错字）| 4 / 30 = 13.3% |
| 偏严（维度归错 / 截断漏看）| 3 / 30 = 10.0% |
| 难判（需 full chunks 验证）| 5 / 30 = 16.7% |

### Judge 系统性偏差（4 类）

#### 1. ⚠️ Judge 自己 hallucinate 错字（最严重）

| QID | Judge 声称错字 | 实际 |
|---|---|---|
| Q033 | "原文'游憩'被误写为'游患'" | 回答里就是"游憩" |
| Q067 | "原文'宜案用'被改为'宜采用'" | "宜案用" 本身不是中文词 |
| Q084 | "原文为'路同密度'" | 应为"路网密度" |

#### 2. PDF OCR 锅被算到 LLM 头上

- Q090 "定牌" — chunks 中 PDF OCR 把某词识别成 "定牌"，**chunks 本身就错**

#### 3. 维度归错

- Q021 "280m 符合宜" 是**业务逻辑错**（280 < 300 下限），应归 dim7 而非 dim4

#### 4. chunks 截断漏看

- Q066 JGJ 286-2013 内容是 W5 D2 入库 spec，但 `original_text[:200]` 截断让 Judge 漏看

### 校正后的"真实 veto"

```
表面 veto: 35
扣除明显错杀 (13.3%): ~5
扣除偏严 (10%): ~3
难判按 50%: ~3
真实 veto ≈ 24 条
```

仍 > 0 → 即使 Judge 修订，veto = 0 仍不达成。

## 八、AIPM 启示候选（5 个）

### 启示 45 候选 · 综合得分与 veto 是两个独立验收维度

W5 D3 实证：综合 86 高（远超 GREEN 75）但 veto 35 阻挡 GREEN — **表层指标好不代表 RAG 可上线**，必须看一票否决。这是产品验收"AI 法条数据库"的核心纪律。

### 启示 46 候选 · LLM 编造的 4 种典型模式

[N] 编造 / 补充说明区编造 / 强条标签编造 / 跨规范联想编造 — 全部可靠 "prompt 硬约束 + 后处理" 治理。这把"编造"问题从"难以根治"变成了"工程问题"。

### 启示 47 候选 · citations vs search 8pp 差距

RAG pipeline 评估必须分两层：
- 检索能不能找到（regression）
- LLM 能不能用对（quality_eval）

单一指标误导决策，**两层分开评估才能定位瓶颈**。

### 启示 48 候选 · LLM Judge 自己也 hallucinate

Judge 凭印象造错字判 dim4=0 — 用 LLM 评 LLM 必须加 "Judge 自我警惕" 约束，否则会产生 ~10-13% 假阳性。

**等价表述**：评测工具本身也是需要"评测"的 — 评测的评测是元评测。

### 启示 49 候选 · PDF OCR 是隐藏的评测干扰项

chunks 里的 OCR 错字会让 Judge 错判 LLM 用词错 — **数据质量是评测可信度的前提**。这把"分块/解析质量"从"工程层"提到了"评测层"。
