# AIPM 转行必备知识 · W1 阶段反思

> **场景**：W1 第一天，从零做一个 RAG 智能规范问答工具
> **角色**：AIPM 课程学员，单人独立开发
> **方法**：与 Claude Code 协同
>
> 本文不是"AIPM 全景路线图"，而是**从昨天这一天实战里抽出的、最高频、最直接见效的能力点**。

---

## 一、AIPM 与传统 PM 的核心差异

| 维度 | 传统 PM | AIPM |
|---|---|---|
| 需求语言 | 功能列表 → 用户故事 | **理想态定义 + 评测体系** |
| 验证手段 | 用户访谈、A/B、转化漏斗 | 评测集（Golden Sample + 一票否决项）+ 在线指标 |
| 与开发对话 | "做这个功能" | "用什么模型 + 怎么 prompt + 怎么评测" |
| 失败模式 | 用户不用 / 转化低 | **模型编造 / 准确率不达标 / 性能不达 SLA** |
| 不可妥协项 | 上线日期、核心流程 | **业务红线（如不编造）+ 评测一票否决** |

**关键洞察**：AIPM 不是"会用 AI 的 PM"，是**对"不确定输出"做产品化的 PM**。LLM 输出是概率分布而非确定逻辑，因此 AIPM 必须先建评测体系，再做功能。

> 在本项目体现：PRD 第二部分专门讲评测体系（7 维度 MOS + 250 条评测集 + 一票否决项），评测体系**先于** RAG 实现写好。

## 二、5 个必备硬技能（按掌握难度排序）

### 技能 1：RAG 全流程的"颗粒度"理解（★★☆）

不需要会调每一个模型，但**必须能讲清每一环干嘛、为何这样选**。本项目栈：

```
PDF 原文
  ↓ Chunker（按"条"切，含强制性识别）
chunks（80–800 字 + 元数据）
  ↓ Embedder（BGE-M3）
向量
  ↓ 向量库（Qdrant）
  ↓ Retriever（top-20 召回）
  ↓ Reranker（BGE-Reranker-v2 精排到 top-5）
top-5 chunks
  ↓ Generator（DeepSeek V3，注入 Prompt + chunks）
回答 + 引用
```

**AIPM 必须能回答**：
- 为什么这里要 Rerank？（向量召回有"语义相近但话题不对"的噪声）
- 为什么不直接拿整本规范喂给 LLM？（上下文窗口 + 成本 + 注意力衰减）
- 检索失败了怎么办？（兜底场景必须设计在 PRD 里）

> 不会写代码可以，但**说不清流程 = 没法跟开发对齐**。

### 技能 2：能定义"评测指标"（★★★）

PRD 已锁定 7 维度：

| 维度 | 含义 | 一票否决 |
|---|---|---|
| 准确性 | 答案与规范原文是否一致 | ❌ 编造 → 否决 |
| 引用完整性 | 引用元数据是否齐 | ❌ 缺规范号 → 否决 |
| 强制性识别 | 应/不应/严禁是否保原词 | — |
| 时效性 | 是否引用现行版本 | — |
| 边界处理 | 8 兜底场景是否命中 | — |
| 表达清晰度 | 是否结构化 | — |
| 性能 | TTFT / 总时长 | — |

**AIPM 必须能做**：
- 把模糊的"答得好"翻译成可量化的 7 维度
- 决定哪些维度是"一票否决"——这是产品价值观的体现
- 设计能跑自动化打分的评测集（含 250 条 query + 标准答案）

> 在本项目体现：评测集 CSV 已先于代码准备好（`docs/初版评测集_使用说明.md`）。

### 技能 3：能与 LLM 协作做技术决策（★★☆）

昨天 chunker 设计阶段，我（PM 角色）面对了 7 个有 ≥2 个合理选择的技术决策：

| # | 决策 | 选项 |
|---|---|---|
| 1 | 规范号来源 | 文件名 / OCR / 数据库映射 |
| 2 | 分类映射 | 手维护 / LLM 分类 |
| 3 | 强制性识别 | 字体 bold / 关键词 / 双重 |
| 4 | 超长条文 | 整条 / 按子项 / 滑动窗口 |
| 5 | 表格向量化 | 直接 embed / + 摘要 / 按行拆 |
| 6 | 附录条文 | 入库 / 不入 |
| 7 | OCR 容错 | 信任 / LLM 修正 / 人工校对 |

**AIPM 必须能做**：
- 让 Claude 列出选项 + 优劣 + 推荐
- **自己判断推荐是否符合产品阶段**（MVP 不该过度工程化）
- 决策入库（commit），让后续改动有审计轨迹

> 这次实战的反例：我（PM 角色）几乎全部按 Claude 推荐选了——这对 MVP 没问题，但 AIPM **应该至少质询 1–2 个决策**，确保自己理解了取舍而不是盲从。

### 技能 4：Prompt 工程的工程化思维（★★★）

CLAUDE.md F 模块定下的规矩：

```
所有 Prompt 集中在 backend/app/core/prompts.py
禁止散落到其他文件
任何修改必须 commit 写明原因 + 跑评测验证
评测分下降则回滚
```

**AIPM 必须理解**：
- Prompt 是**代码资产**不是"调一下文案"——版本化、评测化、不可乱改
- System Prompt 是产品价值观的最直接表达（如本项目的"绝不编造 + 保留原文用词"）
- Prompt 改动 → 评测集回归测试 → 才能上线

> 在本项目体现：`SYSTEM_PROMPT_MAIN` 的 7 条规则已经把"红线"翻译成了 LLM 听得懂的语言。这步是 PM 出的活，不是开发出的活。

### 技能 5：边界处理 / 兜底场景设计（★★★☆）

通用 LLM 失败的常见姿势：
- 用户问"你好" → 不该走 RAG
- 用户问"我项目能违反规范吗" → 不该给"规避建议"
- 检索没结果 → 不该硬答
- 规范作废了 → 不该当现行规范引用

PRD 列了 **8 类兜底**，每类对应固定话术 + 引导方向。

**AIPM 必须能做**：
- 在 PRD 阶段就**穷举不利场景**（用户偏门问、敏感问、超范围问）
- 给每类场景设计「拒绝 + 替代方案」话术
- 把兜底命中率作为评测一票否决项

> 这是 AIPM 与传统 PM 最显著的不同：传统 PM 主要设计「主路径」，AIPM 必须把「主路径以外的 80% 长尾」全部覆盖到。

## 三、3 个必备软技能

### 软技能 1：能写"硬约束文档"（即 CLAUDE.md 这种）

传统 PRD = 描述要做什么。AIPM 还要写：

- **红线文档**（业务上不可碰的）
- **决策快照表**（技术栈锁定理由）
- **协作规则**（什么时候 PM 拍板、什么时候 PM 必须先停下来问）

> 本项目 CLAUDE.md 就是这种文档，明确写了「不允许编造」「不擅自换技术栈」「不确定时停下来问」三类红线。

### 软技能 2：能识别"边际收益递减"的时机

W1 Day 1 修 chunker 时，我经过 4 轮迭代收敛到 62 chunks。继续修能不能到 80 chunks？也许能。

**但**：
- 当前已经能进 W1-T2 阶段验证端到端闭环
- 章节归属错乱不影响 chunk 内容
- 全部 43 部 PDF 跑完会暴露更多多样性问题，**那时再统一修更划算**

**AIPM 必须能判断**：什么时候是"再优化一轮"，什么时候是"停手往下走"。

> 反例：纯算法 PM 容易陷入"指标洁癖"，把 mandatory 准确率从 85% 调到 92%，但忽略了下游还没验证。

### 软技能 3：协作时给 Claude 写好任务

什么样的提问能让 Claude 输出高质量代码：

| 差的提问 | 好的提问 |
|---|---|
| 「写个分块器」 | 「按 docs/design/chunker_design_v0.1.md 的 7 项决策实现 chunker.py，输入是 PDF 路径 + domain，输出是 list[Chunk]，硬约束 max 800 字 / min 50 字」 |
| 「修一下 bug」 | 「跑试金石后强制性条文识别为 0，怀疑是 OCR 后 bold 丢失，请用 pymupdf 直接 dump page 5 的 spans 字体信息验证」 |
| 「检查代码」 | 「按 CLAUDE.md C.2 检查：是否有 print 调试、是否有裸 except、是否硬编码 URL、外部调用是否有 try/except」 |

**AIPM 必须能做**：
- 给上下文（文档路径、约束、目标）
- 给可验证的成功标准（数字、断言）
- 给思考的脚手架（"先列方案，再选"而不是"直接做"）

## 四、AIPM 工作流模板（实战版）

从本项目抽出的 4 阶段工作流，可复用到任何 AI 产品：

```
阶段 1 · 理想态定义（最关键，最容易跳过的一步）
  ├─ 5 维框架（用户/场景/输入/输出/边界）
  ├─ Golden Sample（≥ 5 个典型场景的标准答案）
  ├─ 红线清单（不可碰的）
  └─ 边界穷举（8 类不利场景）

阶段 2 · 评测体系（先于代码）
  ├─ N 维度评分（含一票否决项）
  ├─ 评测集（≥ 50 条覆盖主流场景）
  └─ 评测脚本（自动跑 + 人工抽检）

阶段 3 · 技术决策（PM + 开发 + AI 协作）
  ├─ 列出每个有 ≥2 选择的决策点
  ├─ 选项对比 + 推荐项 + MVP/V2 标注
  └─ 决策入 git，可审计

阶段 4 · 迭代上线
  ├─ MVP 跑通 → 评测 → 修复 → 二轮评测
  └─ 灰度上线 → 监控 → 用户反馈 → 评测集扩容
```

## 七、W2 Day 1 实战追加（2026-05-27 下午）

> 接完 DeepSeek、做完 SSE 端点、加完 3 类兜底之后的新观察。

### 新洞察 1：**System Prompt 是产品规则的"代码化"，不是文案**

W1 写的 SYSTEM_PROMPT_MAIN 7 条规则，今天在生产环境**第一次自证**：

> Query：「居住区配套幼儿园的服务半径不应大于多少米？」
> 检索召回 5 个 chunks，全部不含"300m"具体数值。
> LLM 主动返回：「未在现行规范库中查询到该问题的依据。依据说明：[1] 涉及...，[2][3][4][5] 涉及...，均未包含'幼儿园服务半径'的具体数值规定。」

这条回答**完全是 Prompt 规则 1（不编造）+ 红线 1 触发的结果**——而不是 LLM "刚好不知道"。

**对 AIPM 的启示**：
- Prompt 不是"调一下文案"那种轻量任务
- 它是把产品价值观（不编造、保留原文用词、引导咨询主管部门）**翻译成 LLM 可执行的规则**
- 每条规则都要能在测试用例里验证生效

### 新洞察 2：**检索 hit ≠ 答得对**——两层指标的分离

Hit Rate@5 = 100%，但上面那条 query "答不出来"。原因是 chunk 召回了相关条文，但具体数值在另一个 chunk 里。

**AIPM 必须区分**：

| 层 | 指标 | 衡量什么 |
|---|---|---|
| 检索层 | Hit Rate / Recall / MRR | 相关 chunk 是否进 top-k |
| 生成层 | 答案正确率 / 引用准确率 / 强制性词保留率 | 基于 chunks 能否产出对的答案 |

只看 Hit Rate 容易自满。完整的 AI 产品评测必须**两层独立打分**。

> 在本项目体现：PRD 评测体系把"检索层 6 指标"和"生成层 7 维度 MOS"分开设计，今天验证了这种分层的必要性。

### 新洞察 3：**短路优化是 AI 产品的"边际成本"思维**

发现：闲聊 + 超范围 query 走完整 RAG 链路要 ~2 秒 + 1 次 LLM 费用。
处理：60 行 Python 正则识别，**0 ms 拦截**。

**对 AIPM 的启示**：
- AI 产品的成本结构和传统 SaaS 不同——每次 LLM 调用都有美金成本
- AIPM 要预判**哪些 query 不值得走完整流程**：
  - 闲聊（30% 用户测试时会先打个招呼）
  - 超范围（电影/做菜/翻译类显然非业务）
  - 检索为 0（明确告诉用户不在覆盖范围更礼貌）
- 这种"前置拦截层"应该写进 PRD 的功能架构图

### 新洞察 4：**API 契约要早冻结**

今天 30 分钟写完 SSE 端点，事件结构定下来：
```
retrieval → token... → citations → done | fallback | error
```

如果留到 W3 再做，会有 3 个问题：
- 前端等接口卡进度
- 后端为了赶进度漏入参校验
- 双方对事件顺序有口头约定但没文档

**AIPM 的判断点**：什么时候开放对外 API？
- 主流程跑通（不是完美）就该开放
- 接口字段写进 schemas（Pydantic）作为单一真相
- 即使内部实现还在变，**对外契约要稳定**

### 新洞察 5：**依赖管理的"分阶段验证"**

今天踩了 2 次同类坑：requirements.txt 写了的包但 venv 实际没装：
- W2-G 阶段才发现 openai 没装
- W2-I 阶段才发现 fastapi/uvicorn 没装

**教训**：
- requirements.txt 是"目标清单"，不是"现状清单"
- 每个阶段进新依赖前先 `pip list | grep` 验证
- 复杂项目用 `pip-compile` + `pip-sync` 锁定，但 MVP 阶段可以接受"按需装"

**对 AIPM 的启示**：研发环境的"完整性"是个隐性维度。AIPM 不需要管 pip 命令，但要意识到：
> 开发者说"装完依赖了"≠ 系统真的能跑

定期跑端到端冒烟测试，比口头确认更可靠。

## 十、W2 Day 2 实战追加（2026-05-29）

> 这一天主线做了两件事：把后端 RAG 包装成完整 HTTP 服务能被前端消费、把抽象的"引用 + 原文"变成用户能"点 → 跳"的真实体验。
>
> 5 个新洞察，按"对 AIPM 帮助度"排序。

### 新洞察 9：**「可溯源」才是 RAG 产品和聊天机器人的本质区别**

W2 Day 2 加上 `/api/spec/{spec_code}` PDF 端点 + 前端"📄 查看原文 第 N 页 ↗"按钮之后，整个产品才真正配得上"AI 版规范法条数据库"的定位。

之前的 SSE 流 + 引用卡片只是"展示出处"。今天才是"可验证出处"：

| 用户体验 | 时间 | 是什么产品 |
|---|---|---|
| 看到答案 → 复制规范号 → 打开浏览器 → 搜 PDF → 翻页找到原文 | 5 分钟 | 聊天机器人 |
| 看到答案 → 点 `[1]` → 看到引用卡 → 点"查看原文" → PDF 跳到该页 | **3 秒** | **AI 法条数据库** |

**对 AIPM 的启示**：RAG 产品的差异化不在"能引用"，而在"引用能 1 秒内被验证"。**整个'验证'闭环必须是产品 P0**，不是"V2 再加"。

### 新洞察 10：**设计 Token 化是产品快速变体的杠杆**

用户开局只用了 1 张同济蓝色块图作输入，整个主题切换只动了 12 行 CSS 变量（`--primary` / `--sidebar` 系列），所有组件零修改。

如果当初用 hex 直接写在 50+ 个组件里，今天就是 8 小时的工作量。

**对 AIPM 的启示**：在 PRD 阶段就要强制要求"设计稿用 Design Tokens 而非具体 hex 值"。这一句要求，让后续主题切换 / 暗黑模式 / 客户定制成本从"重做 UI"降到"改 10 个变量"。

### 新洞察 11：**AI 协作要画清"暗示 vs 显式"的边界**

用户给了"换成同济蓝"+"用同济 logo"两个 brief。

- "同济蓝" 是颜色（不可注册商标），照单全收 → 改 12 个 token
- "同济 logo" 是受商标保护的具体校徽 → **我必须停下来问**

我做的处理是给 4 个备选 + 推荐"原创致敬"方案。用户选了 B（原创），最终交付：
- ✅ 圆形（基础几何，没有任何特定 IP 含义）
- ✅ 同济蓝（颜色非商标）
- ✅ 通用字符"同"（常用汉字）
- ❌ 没复制具体校徽的舟楫 / 拉丁文绕环 / 任何特定造型

**对 AIPM 的启示**：在向 AI / 设计师 brief 时要主动列两类清单：
- **可借鉴的暗示元素**（色彩 / 整体格调 / 字体风格）
- **必须原创的具体造型**（图形元素 / 字体本身 / 特定符号）

AI 在没有明确边界时容易越线，PM 要先把边界画清楚。

### 新洞察 12：**「优雅降级」是 AI 产品的必修课**

今天 Reranker 模型卡在 998MB 下载没完成，整个 query 直接挂住。

幸好 pipeline 写了 `try/except` + env flag `RERANK_ENABLED`，把它关掉后系统立刻回到纯向量召回的可用状态。

**对 AIPM 的启示**：每个 AI 子模块都要有"开关 + 降级路径"，而且开关要：
- 能在不重启的情况下生效（V2 可加 admin 接口）
- 能区分"完全关闭"和"出错时回退"两种语义
- 关闭后的体验要明确告诉用户"功能降级"，不假装一切正常

这点和金融系统的"熔断 + 降级"是同一种思维。AIPM 必须把传统软件工程的可靠性理念引入到 AI 链路里。

### 新洞察 13：**单一数据源 + 状态短路 = 前端不混乱**

前端 chatStore（zustand）做了一个很小但关键的设计：**只有"最新一条 assistant 消息"的引用能响应正文 [N] 点击**。

历史消息的 `[1]` 不再可点击，是为了避免：
- 历史第 1 条的 [1] 和最新第 5 条的 [1] 冲突高亮哪个？
- 引用编号在右栏滚动到错位置

**对 AIPM 的启示**：前端状态设计时，**列出所有"两个用户操作冲突"的场景**，主动选一个"语义清晰的简化版"而不是"全功能但混乱"。这是产品力的体现，不是技术问题。

## 十二、W2 Day 3 实战追加（评测体系首跑后的洞察）

> 今天首次跑出评测数字：38 条 Hit Rate@5 (loose) = 47.4%。**前 5 个洞察都是从这个数字怎么来的、为什么是这个数字、如何让它更有用三个角度抽出的**。

### 新洞察 14：**"5% Hit Rate" 是评测的第一课**

数字本身没意义，**"为什么是 5%"才有意义**。20 条小样本跑出 strict Hit@5 = 5% 后，第一反应是"检索弱，改 retriever"——但深挖才发现是**评测集和规范库错位**（错怪检索）。

**AIPM 用例**：评测数字异常时，按顺序排查：
1. 评测集 expected 与实际数据资产是否一致？（最容易被忽略）
2. 匹配规则是否过严？（strict vs loose）
3. 数据预处理（如 OCR）是否污染了字段？
4. **最后才是算法（embedder/reranker）问题**

跳过 1-3 直接优化算法，会越改越偏。

### 新洞察 15：**测什么 = 工具决定能力的边界**

评测集 v1 在准备日就做完，但今天才发现"问对了问题，定错了答案"。**评测集本身没人评测过**。

**AIPM 制度建议**：评测集发布前必须做 2 个动作：
- **半自动对账**：用脚本扫一遍 expected_spec 是否都在库 → 错位率统计
- **样本试跑**：抽 5 条人工跑一遍，看检索结果是否"明显合理"

否则评测集就是"漂亮的占位符"。

### 新洞察 16：**数据集 ↔ 系统 必须周周对账**

错位发生在：
- 评测集设计时心目中的"标准规范清单"（GB 50016-2014 等老国标）
- ingest 实际入库的清单（GB 55037-2022 等新通用规范）

两份清单从来没碰过头，直到第一次跑评测。

**AIPM 制度建议**：每周末跑一次 `inventory_diff`：
- 列"评测集期望但库里没有的规范"
- 列"库里有但评测集没覆盖的规范"
- **强制 reconcile**，并在 git 里留痕

这件事不做，迟早被错位坑一次。今天就是。

### 新洞察 17：**指标双轨制（strict + loose）**

- `strict Hit@5` = spec_code AND clause 双匹配（看精度）
- `loose Hit@5` = 仅 spec_code 匹配（看召回）
- 当 **strict ≪ loose**（如今天 2.6% vs 47.4%）→ 数据预处理/分块/编号精度问题主导
- 当 **strict ≈ loose** → 召回质量问题

**AIPM 用例**：双指标一起看才能定位**问题的层次**。今天 strict 远低于 loose，定位 OCR 条文编号是首要 fix；如果 strict ≈ loose，会去优化 embedding/reranker。完全不同的 W3 计划。

### 新洞察 18：**Reranker 的价值必须用数字证明**

加 reranker 之前直觉是"提升 20%"，今天实测：

| 域 | rerank 提升 |
|---|---|
| 总体 | +2.7pp |
| **规划** | **+7.6pp** ⭐ |
| 消防 | 0（已饱和 100%）|
| 综合（跨规范）| 0（无能为力）|

**AIPM 用例**：决定"是否上 reranker"不能凭直觉，必须看数字。同样适用于"是否上 hybrid 检索 / multi-vector / query 改写"——任何加复杂度的动作都要有数字证明 ROI。

## 十三、新方法论 · 数据 ↔ 评测 ↔ 系统 三角对账

这是今天最大的方法论突破，单列一节。

### 三角关系

```
        评测集（PM 定义的"应该测什么"）
           ▲                ▲
           │                │
           │                │
   规范库（数据资产）  ◀──▶  RAG 系统（实现）
                              （Embedder + Retriever + Reranker + LLM）
```

每两个之间都可能错位：

| 错位 | 症状 | 检测 | 修复 |
|---|---|---|---|
| 评测 ↔ 数据 | strict + loose 都低，错例集中在"期望的规范不在库" | `inventory_diff` 脚本 | 改评测集 or 扩规范库 |
| 数据 ↔ 系统 | strict 远低于 loose，错例集中在"规范在库但 chunk 字段乱" | 抽样 grep chunks | 修 chunker / OCR |
| 评测 ↔ 系统 | loose 高但 strict 低 | 看 chunks 是否在 top-K（绕过 expected_clause）| 修 expected_clause |

**AIPM 必须主动设计三角对账机制**，否则迟早某一边出错。

### 周末 reconcile checklist

每周末跑一遍：

- [ ] 评测集所有 expected_spec 是否都在库？（错位率 < 5% 通过）
- [ ] 评测集 expected_clause 是否能在对应 chunks 里 grep 到？（OCR 污染率 < 10% 通过）
- [ ] 上周 best score 是否能复现？（防止某次 ingest 静默回归）
- [ ] 新增的入库规范，是否需要补评测题？

## 十五、W3 三天浓缩 · 11 个新洞察（按主题分组）

W3 三天（D1 诊断 + D2 query 改写 + D3 hybrid 失败）累计 **11 个新洞察**，按 4 个主题分组。

### 主题 A · 诊断纪律（启示 14, 22）

#### 启示 14 · 诊断要诚实，不要"假设驱动开发"

**场景**：W3 D1 我最初确信 strict Hit@5 只有 2.6% 是 "OCR 烂"导致的，准备直接开干"重 OCR"。停下来做 5 轮诊断后发现：
- OCR 字符错全库 < 0.1%
- OCR 编号乱全库 < 0.5%
- 数据库重复入库 0
- **真正主因是 chunker `_dN` 后缀机制让 text 重复 + BGE-M3 在专业规范的语义偏**

**反例代价**：如果不做诊断，今晚就花 3-4h 装 PaddleOCR / Marker / MinerU 重 ingest 全库，**4 小时后发现解决不了主要问题**。

**纪律三条**：
1. 不下结论前先量化（不仅看错例，要全库统计）
2. 每个假设都要能被数字证伪
3. **当数字与直觉冲突时，相信数字**

#### 启示 22 · 数据驱动决策的极端版本

**场景**：W3 D3 装 BM25 时几乎所有 RAG 教程都说"必加 hybrid"。如果按"经验/直觉"做决策：
- 装 BM25 → 上线 → 真实用户问"280m 合规吗"召回质量下降，没人知道是 BM25 干的
- 半年后某个用户投诉，复盘才发现是融合策略错

**今晚 15 分钟评测就发现 BM25 在我们数据上 -2.6pp**。
**评测体系跑通后，做任何"业界建议优化"都先量化**——15 分钟评测能省 6 个月回滚成本。

**反例对照**：

| 决策方式 | 代价 |
|---|---|
| 经验/直觉驱动（"大家都加 BM25"）| 上线后才发现，回滚 + 找人 + 复盘 = 数月 |
| **数据驱动（15min 评测）** | **立刻发现并停止，0 上线代价** |

### 主题 B · 评测视角拆分（启示 16, 17, 18）

#### 启示 16 · 召回与精度是两条独立赛道

W3 D1 评测：Hit@5 loose 47.4% / strict 2.6%，**召回 50pp、精度差 45pp**。

- 召回层先做对（找对 spec_code）
- 精度层才有意义（找对 clause）
- **如果一开始盯 strict 优化，等于在召回还没及格时刷精度——错的层级**

#### 启示 17 · "正确归因" 比 "总体涨多少" 更重要

W3 D2 multi-query 总体只涨 +2.6pp 看着不亮眼，但拆开：
- **规划 +7.7pp** 是真改善
- **显性事实 +5.6pp** 是真改善
- 综合 0pp 是"病在别处"（评测集 + 规范库不匹配）
- 对抗 0pp 是"病在别处"（LLM 推理能力，非检索）

**如果只看总体，会下错结论 "multi-query 没用"**。

**AIPM 视角**：任何评测结果都要拆分维度看，找出"被平均掉的真实效果"。

#### 启示 18 · 不要为难"病在别处"的指标

综合域 0% 和对抗 0%，**无论怎么折腾检索都不会涨**。

正确做法：
1. 承认这些是别的层级的问题（评测集 / LLM / 规范库不全）
2. 标注好，不要花时间在错误层级
3. 把目标和注意力放在能改的指标上

**反例**：花 W3 D2 一天试图救综合域 0% → 改 chunker / 改 retriever / 改 reranker 全无效，因为问题在评测集 expected_spec 不在库

### 主题 C · 失败的价值（启示 15, 21, 23）⭐ W3 最大收获

#### 启示 15 · "改了不涨" 也是成果

W3 D1 dedup 改完 Hit@5 没动，看起来"白干"。但：
1. 排除了一个潜在主因（节省后续 3-4h 诊断时间）
2. top-10 strict +2.6pp 真实改善
3. 为后续 query 改写 / hybrid 提供干净的基础设施

**评测体系最大价值不是"算涨了多少"，而是"算出哪些动作没用"**——后者帮你停止浪费时间。

#### 启示 21 · "改了反而劣化" 是更宝贵的成果（W3 D3 BM25 失败）

W3 D3 加 BM25 hybrid 反而 -2.6pp。但失败比单纯的"没涨"价值更大：

1. **场景适配 > 技术先进性**：BM25 在通用 RAG 文献里"必加"，但在我们"问数值是否合规"型评测集上是负优化
2. **暴露隐藏的数据偏差**：评测集 70% query 是"问具体数值合规"，BGE-M3 + 多 query 已足够，BM25 反而干扰
3. **教会未来的自己 / 同事**：日志里写明失败模式后，**下次有人想加 BM25 时 5 分钟读完就能避坑**

**AIPM 视角**：
- 失败的价值 > 没尝试的"看起来更好"
- 排除一个错误方向 = 节省 6 个月真实工程时间

#### 启示 23 · 失败要诚实记录，不要藏

工程师常犯的错：
- "嗯，BM25 我试了但效果不好，删了不提"
- 半年后另一个工程师又想到"应该加 BM25"，又试一遍

**今天日志写明"为什么 BM25 在我们这里失败" + Q021 具体 case，比单纯关掉它价值大 10 倍**。

**记账格式**：
1. 假设是什么
2. 实验方案 + 参数
3. 数字对照（明确的 Δ）
4. 至少 1 个 row-level case 暴露根因
5. 失败原因分析（不是"效果差"，是"为什么差"）
6. 处置：保留 / 关闭 / 删除（选 + 理由）

### 主题 D · 工程师的成熟度（启示 19, 20, 24）

#### 启示 19 · 工程债要立刻记账，不要"以后再说"

W3 D2 multi-query 让时延翻倍 3.4s → 6.8s。如果不立刻在 **6 个地方** 标记，下周就忘了：

1. CLAUDE.md / 设计文档（架构债）
2. 开发日志（决策记录）
3. Task 列表（待办事项）
4. commit message（git 历史可搜）
5. TODO 注释（代码里直接看到）
6. AIPM 必备知识（方法论级）

**冗余是为了不丢**。债务总是被"想着以后再做"耽误。

#### 启示 20 · LLM 改写效果跟 prompt 示例质量强相关

W3 D2 query 改写 prompt 设计时，3 个 in-context 示例直接定型了 3 个固定视角输出。如果示例混乱，输出会发散偏题。

**做 prompt 时的"示例工程"** 比"指令工程"更关键：
- ❌ 写一大段指令："请根据语义扩展..."
- ✅ 写 3 个典型示例 + 输入输出格式

**示例是 LLM 真正学习的范式。**

#### 启示 24 · "保留代码 + 默认关 + 文档解释" 是失败实验的正确处置

W3 D3 hybrid 失败，但**不该删代码**：

| 选项 | 评价 |
|---|---|
| ❌ 删 bm25_indexer.py 整段 | 下次想试需要重写 145 行 |
| ❌ 留默认开 | 拖累生产 -2.6pp |
| ✅ **env flag 默认 false + 代码完整保留 + config 详细注释** | 一键启用 + 留路径 + 不增加 SLA 风险 |

**3 个不可少**：
1. env flag（一键启用 / 关闭）
2. config 注释解释为什么默认关 + 哪种场景可能有效
3. 详细失败日志（含 row-level case）

下次数据集 / 业务场景变化，翻 flag 即可重新试，**不需要重新写代码**。

## 十八、W3 收尾补全 + W4 数据资产周 · 12 个新洞察（25-36）

v4.0 文档结构只覆盖到启示 24（W3 D3 hybrid 失败）。

### A · W3 D4 reranker 调参失败（启示 25-28）

#### 启示 25 · "诊断假设 ≠ 改造假设"（最深的失败模式）

W3 D4 诊断到位（"Q010 在 reranker 输入 rank 10"是事实），但改造方案（"扩 candidate_k + 改 passage 格式 → reranker 排上来"）**未经验证**。

**AIPM 必须分离两层**：
1. **诊断层**（事实，可验证）
2. **改造层**（假设，需小样本验证）

**正确做法**：诊断完成后，**先在 1-2 个 case 上验证改造能否真的解决**，再扩到全量评测。

#### 启示 26 · 黑盒模型的"参数调优天花板"

reranker / embedding / LLM 都是预训练黑盒，参数调优（输入格式、temperature、top_k）的有效性**有限且不可预测**。

工程视角的 4 层应对：

| 层 | 手段 | 效果上限 | 成本 |
|---|---|---|---|
| 1 | 参数调优 | ~10pp | 最低 |
| 2 | prompt engineering / 输入工程 | 5-20pp | 低 |
| 3 | 微调 fine-tuning | 20-50pp | 高（要标注）|
| 4 | 换模型 / 自己训练 | 最高 | 最高 |

**W3 D4 撞在第 1 层天花板**——当前架构下接受 strict 物理极限，要解锁必须升到 3-4 层。

#### 启示 27 · "连续失败"的纪律

W3 D3 失败 + W3 D4 失败连续 2 天 0 进展，工程师容易：
- 急躁：随便加路径试试
- 放弃：转向看似简单的事
- 自我怀疑

**正确处置**：
1. 立刻停下来 reconcile（连续失败说明假设链有系统性问题）
2. 重新审视目标可行性（strict ≥ 30% 是否本就不可能？）
3. 接受 baseline，转攻其他能进步的维度

#### 启示 28 · "保留代码 + env flag" 成方法论标准

W3 D3 学的"保留代码 + 默认关 + 文档解释"，W3 D4 立刻复用：
- `RERANK_CANDIDATE_K` env / `RERANK_PASSAGE_FORMAT` env
- `_build_passage()` 完整保留

**3 个不可少**：env flag 一键启用 + config 注释解释默认值 + 详细失败日志（含 row-level case）。
未来换 reranker 模型时可当场重新评估，**不需要重写代码**——这就是失败实验的复利。

### B · W3 D5 K 完整版兜底（启示 29-32）

#### 启示 29 · "礼貌拒答"是 AI 产品的核心能力

很多 AI 产品犯的错：**所有问题都瞎答**。
真正成熟的产品有清晰边界感：
- **能力边界**（"超范围 → 引导"）
- **合规边界**（"敏感 → 拒答 + 引导咨询主管部门"）
- **时效边界**（"废止 → 提示现行版本"）
- **信息边界**（"模糊 → 主动追问"）

4 类边界让产品 **值得信任** —— "AI 法条数据库" 的定位才能真正立住。

#### 启示 30 · 优先级链是兜底设计的核心

8 类全覆盖最难的不是"识别每一类"，而是**多类同时命中时怎么选**。

例：`"GB 50180-93 怎么规避审查？"` 同时命中 deprecated + sensitive。
**应该走哪个**？W3 D5 设计 **sensitive > deprecated**——用户意图核心是"规避"，先拒答规避。

整个优先级链：
```
input_invalid → sensitive → deprecated → chitchat → out_of_scope → ambiguous → normal
```
每个相邻位置的选择都是 **产品价值观的体现**。

#### 启示 31 · 分段判定 > 单一阈值

W3 D5 ambiguous 判定从"硬阈值 < 8 字"改成**三段**：
- < 4 字：必模糊
- 4-15 字：关键词组合判断
- > 15 字：默认放行

**单一阈值的陷阱**：永远会有 1 个边界 case 让你纠结调高调低。
**分段判定**让每段有自己的逻辑，避免"为救一个 case 调阈值反而打破另一个 case"。

#### 启示 32 · TODO 不只是注释，是技术债的可见性

W2 D1 留的 TODO 在 W3 D5 完成。如果当时没在 scenario.py 写明 `⏸ ambiguous (TODO W3)`，今天大概率会忘记补这 3 类。

**TODO 写得好的标准**：
1. 标明属于哪个迭代（W3、W4 等）
2. 写明为什么没做（"简版先跑通"）
3. 写明应该怎么做（具体的关键词 / 文案方向）

**工程债的可见性 = 长期演进的纪律。**

### C · W4 D2-D3 数据资产周（启示 33-36）⭐ 最近收获

#### 启示 33 · 数字会骗人，评测集是镜子（W4 D2）

W3 D2 涨 +2.6pp 是 **RAG 变好**。
W4 D2 涨 +30.6pp **不是 RAG 变好**——是**评测集变可信了**。

| 阶段 | RAG 能力 | 评测集质量 | 测出的数字 |
|---|---|---|---|
| W3 末 | 50% | v2（16 条废条拖累）| **50.0%（偏低）** |
| W4 D2 | 50%（不变）| v3（废条修复）| **80.6%（真实）** |

**v2 50% = "RAG 能力 × 评测集有效率"**。v3 才反映 RAG 真实能力。

**AIPM 容易陷入的错觉**：
- ❌ "Hit@5 50% 太低了，得调算法" → W3 D3/D4 折腾算法全失败
- ✅ "Hit@5 50% 太低了，先看评测集本身" → W4 D2 修评测就涨 +30pp

**结论**：在大动算法之前，先确认评测集**每一条都可被验证**——这是最便宜的"涨数字"手段。

#### 启示 34 · 评测集是循环可信化的（W4 D3 part 1）

```
v1 (50 条) → 跑评测 → 发现 16 条 spec 不在库
  ↓
v2 (修 spec) → 跑评测 → strict 仍偏低
  ↓
v3 (3 路径修 16 条) → 跑评测 → 14 条 expected_clause 错位
  ↓
v3.1 (修 14 条 clause) → strict 翻倍 16.1% → 32.3%
  ↓
v4 (扩量) → 预期再暴露新瑕疵
```

**做评测集像剥洋葱** — 每一层修订都让数字更接近真实。

**实操经验**：不要追求"一次性写完美评测集"，应该**先快速跑 + 看错例 + 局部修**，循环 3-5 轮才能稳定。

#### 启示 35 · 评测集是双向探针 — 测 RAG 也测 pipeline 盲点（W4 D3 part 2）

W4 D3 part 2 用 16 条 fallback 评测**揪出 scenario.py 5 个 bug**：
- chitchat 正则末尾不含中文语气词（"你好啊"miss）
- chitchat 自我介绍漏"这个系统"类
- sensitive `过审` 距离不够
- sensitive 漏"偷偷"独立词
- deprecated regex 在四位年份"1999"失败

**评测集不是被动验证工具**：
- W4 D2 启示 33（单向）：评测集质量提升 → 数字可信化
- W4 D3 part 1 启示 34（循环）：评测集质量循环可信化（v1→v3.1）
- **W4 D3 part 2 启示 35（双向）：评测集 → 暴露系统盲点 → 修系统**

**核心**：评测集是**主动暴露系统盲点的探针**，是 AIPM 最有杠杆的产出物。

#### 启示 36 · "温柔挑战"是 AI 协作的关键环节（W4 D3 part 2）

用户审核 16 条 query 草案后说"感觉没问题"。
我（Claude）温柔挑战："**评测集是镜子，没跑过的都是猜的**" → 实跑揪出 5 个 bug。

**AIPM 协作的 5 步流程**：
1. AI 列草案（候选 query + 设计理由）
2. **用户审核**（判断"看起来"对不对）
3. **AI 温柔挑战** → 实跑验证（让数据说话）
4. **用户决策**（修系统 vs 改评测集 vs 双向）
5. AI 实施 + 回归测试

**为什么这个流程值得固化**：
- 用户的"看起来没问题"是直觉，AI 的"实跑数据"是事实
- AIPM 训练真正发生的地方不是直觉，而是**直觉与数据冲突时的决策**
- AI 不挑战 = 帮凶。AI 太凶 = 不友好。"**温柔挑战**"是关键平衡

## 二十一、W4 D4 实战追加（多组合矩阵 + 假阳性揭穿）· 4 个新洞察（37-40）⭐⭐

### 起因

W3 D2 报告 multi-query "+2.6pp loose"，作为 SUCCESS 沉淀进 commit / devlog / AIPM v4.0 启示 17。
W4 D2-D3 修对评测集 v3.1（启示 33-36）后，W4 D4 在 v3.1 上做 **6 组合矩阵复测**——揭穿了一个**潜伏 4 天的假阳性**。

### 启示 37 · "评测集变化触发全链路重审"

v3.1 6 组合 A vs B 数字完全相同：
- A (mq=on, rk=on, hyb=on): strict 32.3% / loose 80.6%
- B (mq=off, rk=on, hyb=on): strict 32.3% / loose 80.6%

W3 D2 报告 "+2.6pp loose" 在 v3.1 上完全无法复现。

**根因**：v2 集 16 条废条造成 multi-query 的 3 变体"广撒网"恰好命中其中几条"相似 spec"，造成假阳性。v3.1 修对后没了。

**教训**：评测集变化后，不只看"总体数字涨多少"，还要 **逐个复测上层实验结论**。否则会出现 **"基于假阳性的算法决策"作为隐藏技术债**。

### 启示 38 · 多指标 + 多维度才能看清模型行为

W3 D3 看 loose 一个数字判定 "hybrid 是负优化"。
W4 D4 看 strict + loose 双轴，发现 hybrid 是 **双面刃**：
- A vs E (hyb on→off): strict +3.2pp / loose **-3.3pp**

W3 D3 没观察到 hybrid 帮 strict 这一面。单一指标视角下"-2.6pp"是一个数字；多指标 + 多维度视角下，**"-2.6 loose / +3.2 strict / 规划 +9.1pp / 综合 0pp"是一个决策面**。

**等价表述**：评测不只看一张表，要看 **strict / loose / MRR / by-domain / by-difficulty 全方位拼图**。

### 启示 39 · "假阳性"比"失败"更隐蔽 ⭐⭐（W4 D4 最重要洞察）

| 实验类型 | 反馈速度 | 沉淀风险 |
|---|---|---|
| W3 D3 hybrid 失败 | 当天 -2.6pp 就发现 | 立刻关默认 + 文档，**0 风险** |
| W3 D2 multi-query "+2.6pp" 假阳性 | **4 天潜伏才揭穿** | 沉淀进 commit / devlog / AIPM 启示 17，**已成技术债** |

**失败实验立刻可见 → 立刻处置；假阳性表现得像成功 → 一直被信任**。

**AIPM 防御性思维**：每个"成功"实验都要做 **延迟回归测试**——评测集更新后重跑，看结论是否仍成立。

**操作建议**：
1. 每周末跑一次 "全部历史 SUCCESS 实验"的回归（v3.1、v4 等新评测集）
2. 凡发现一个假阳性，**立刻倒查它沉淀的所有 commit / doc**——把那些"基于它"做的决策也撤销
3. **回归测试是 AIPM 周末必做项**——不是 nice-to-have，是 must-do

### 启示 40 · 不存在"通用最佳"——业务 KPI 决定配置

W4 D4 6 组合矩阵显示：
- 想要 **loose 最高** → E (mq=on + rk=on + hyb=off) 83.9%
- 想要 **strict 最高** → C (mq=on + rk=off + hyb=on) 35.5%
- 想要 **时延最低** → F (all off) 0.4s
- 想要平衡 → E

**没有"通用最佳"**——AIPM 核心工作是 **对齐业务 KPI 与技术配置**。

对本项目"AI 法条数据库"：loose 关键（先找对规范 > 找对具体条款）→ **E 配置**。
如果业务定位是"严苛精确条文匹配工具"，则 C 配置。
如果是"实时移动场景"，则 F 配置（牺牲 13pp 换 4ms 响应）。

**等价表述**：技术决策的起点不是"哪个算法效果好"，是"我们的产品 KPI 是什么"。

## 二十二、新工程纪律 · 延迟回归测试（防假阳性）

W4 D4 揭穿 W3 D2 假阳性后，沉淀的新工程纪律：

```
每次评测集升级 (v_n → v_n+1) 后：
  1. 跑 v_n+1 上的"all on" baseline 看总体数字
  2. ⭐ 逐个复测历史 SUCCESS 实验：
     for impl in [multi_query, hybrid, dedup, rerank_passage_format, ...]:
         跑 v_n+1 上 impl on/off 对照
         如果之前 +X pp 在 v_n+1 上变成 ±0 → 假阳性，关默认 + 倒查决策链
         如果之前 -X pp 在 v_n+1 上变成 +Y pp → 误判，重新评估
  3. 多指标看 strict / loose / 各域 是否一致
  4. 把"哪些结论仍成立 / 哪些被推翻"写进周报
```

**实操工具**：脚本化"全配置回归"，每个评测集升级后自动跑。
（W4 D5 可考虑写 `scripts/run_regression.py`：循环 6+ 组合 + diff vs 上次评测集结果。）

## 二十四、W5 D1 实战追加（评测集扩量再次揭穿假阳性）· 2 个新洞察（41-42）

### 起因

W5 D1 主线：评测集 v3.1 (50) → v4 (100)，扩 50 条新 query 覆盖入库的更多规范（v3.1 只覆盖 6/39 部）。

**核心挑战**：怎么扩 50 条不引入新的假阳性？

应对：把 W4 D3 part 2 沉淀的"温柔挑战 5 步法"+ W4 D4 沉淀的"延迟回归测试"全程上紧。

### 关键数字（W5 D1 收获）

| 指标 | v3.1 E (31 有效) | v4 E (74 有效) | Δ |
|---|---|---|---|
| **Hit@5 strict** | **32.3%** | **64.9%** ⭐⭐⭐ | **+32.6pp 翻倍** |
| Hit@5 loose | 83.9% | 89.2% | +5.3pp |
| 时延/条 | 4.3s | 2.9s | -32% |

**关键解读**：32.3% → 64.9% **不是 RAG 变好**，是评测集扩量后用了"chunks-aware query 设计"（每条 expected_clause 都预 grep 验证）—— **v4 是首次"完全可信评测集"**。

### 启示 41 · AI 草稿 + 业务专家审 = 不可分割

W5 D1 50 条 query AI 自动生成草稿。但 **6 次业务真实性筛除**：
- **用户 2 次专业反馈**：
  - Q053 "用地分类问法" → 用户："用地分类已固定在 GB/T 21010，应问体量规模"
  - Q056 "流浪未成年人救助中心" → 用户："规划行业没听说过，问社区卫生服务中心"
- **AI 自筛 4 次分类错位**：
  - DB 31T 1557（实是配电网）/ CJJ/T 314（轨道交通）→ 非 5 类规范
  - GB/T 39972（GIS 信息系统）/ JGJ/T 245（白蚁防治）→ 非设计指标

**AI 不懂的底层**：
- "用地分类是 GB/T 21010 固定的"（专业体系认知）
- "流浪未成年人救助中心"在规划行业实际认知度（业务流程）
- "JGJ/T 245 是白蚁防治"（虽然 spec_name 写明但 AI 抽 chunks 时一视同仁）

**等价表述**：**评测集设计永远需要业务专家审**。AI 是协作工具，不是判断主体。
"温柔挑战 5 步法"中"用户审核"那一步是必经路径，不能跳过。

### 启示 42 · 评测集扩量本身可能再次揭穿假阳性

W4 D4 揭穿了一个假阳性（multi-query +2.6pp）。
**W5 D1 又揭穿了一个比假阳性更深的"误判"**：

**W3 D4 报告 strict 调参全 0 改善，归因 "reranker 模型物理上限"（启示 26）**

但今天数据：
- v3.1 E 配置 strict 32.3%（W4 D4 当时认为是"物理上限"）
- **v4 E 配置 strict 64.9%（+32.6pp）**
- 同样 reranker，同样 BGE-M3，**只是评测集扩量 + chunks-aware → strict 翻倍**

→ **"reranker 物理上限" 是评测集瑕疵造成的错觉，真实上限在 65%+**

**4 次评测集质量提升 → 4 次结论被颠覆**：
1. W4 D2 修废条（v2→v3）：揭穿"loose 50% = RAG 上限"误判
2. W4 D3 part 1 修 clause（v3→v3.1）：strict 16.1 → 32.3
3. W4 D4 假阳性揭穿：multi-query +2.6pp 是 v2 瑕疵造的假
4. **W5 D1 扩量（v3.1→v4）**：揭穿 "strict 物理上限 = 32.3%" 误判

**等价表述**：**每次评测集质量提升，都可能颠覆此前的结论**。EDD 闭环必须包含"每次扩量后回归测试 + 复盘历史结论"——这不是一次性动作，是常态化流程。
