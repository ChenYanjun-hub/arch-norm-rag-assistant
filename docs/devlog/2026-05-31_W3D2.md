# W3 Day 2 · Query 改写 + RRF 融合（攻 BGE-M3 语义偏）

**日期**：2026-05-31（周日）
**阶段**：W3 D2
**主题**：用 LLM 把单 query 扩成 3 个变体，4 路 search + RRF 融合
**结论**：规划 +7.7pp / 显性事实 +5.6pp / 总体 +2.6pp，时延翻倍

---

## 一、起因

W3 D1 5 轮诊断定位真正瓶颈：BGE-M3 在专业规范文本上的**语义偏差**。

典型 case Q010：
```
原 query: "办公建筑的耐火等级最低要求？"  期望 GB 55037-2022 5.1.3
但 top-20 全是 5.2/5.3 章节，5.1 直到 rank 11 才出现
原因：BGE-M3 把"耐火等级"匹配到"5.3 防火等级条款"，错过"5.1 耐火分类"
```

**今天攻坚方案**：让 LLM 把"耐火等级"改写为"耐火极限/一级二级分类/多层高层"等多角度变体，多路召回 + RRF 融合。

---

## 二、做了什么

### 1. `prompts.py` 加 SYSTEM_PROMPT_QUERY_REWRITE

设计 3 个固定视角（每个变体负责一种）：
- **变体 1**：同义词/近义词替换（"服务半径" ↔ "配建距离"）
- **变体 2**：补全专业术语和领域背景词（加"民用建筑/建筑分类/高度限值"）
- **变体 3**：把隐含的章节性关键词显化（把"分类"显化为"一类/二类/高层/多层"）

输出格式：JSON 数组 `["变体1", "变体2", "变体3"]`，3 个示例 in-context 引导。

### 2. 新建 `app/rag/query_rewriter.py`

```python
def rewrite_query(query: str, *, timeout: float = 3.0) -> list[str]:
    """返回 [原 query, 变体1, 变体2, 变体3]
    任何失败都降级到 [原 query]，永不抛异常。"""
```

关键设计：
- **non-streaming** 调用（拿完整 JSON 即可）
- **超时 3s**（保 TTFT SLA）
- **temperature=0.4**（比主问答 0.1 高，鼓励多样性）
- **robust 解析**：正则抓首个 `[...]` 数组，容忍 markdown 围栏 / 引号弯转
- **永不抛异常**：失败降级单 query

冒烟测试：
```
"办公建筑的耐火等级最低要求？" (1045ms)
→ [原]
+ "民用建筑办公楼最低耐火等级"
+ "办公建筑 耐火极限 一级二级分类"      ← 这就是救 5.1 的关键
+ "办公建筑高度划分 耐火等级 多层高层"
```

### 3. `retriever.py` 新增 `rrf_fuse()`

业界标准 RRF 算法：
```python
score(d) = Σ_q  1 / (k + rank_q(d))   # k=60 业界经验值
```

优点：
- 不依赖原始 score 量纲（不同 query 的 cosine 分布差很多）
- 对 rank 单调递减，多次命中累加

### 4. `pipeline.py` 接入多 query

流程：
```
detect_scenario 短路（闲聊/超范围不走 LLM）
       ↓
rewrite_query → 4 个 query
       ↓
顺序 embed + search（Qdrant 锁不能并发）
       ↓
RRF 融合 (k=60) → top_k_rough*2
       ↓
现有 dedup → 现有 reranker → top-5
```

加 `MULTI_QUERY_ENABLED` env flag，事件流加 `multi_query / n_queries` 透明度字段。

### 5. `run_eval.py` 加 `--no-multi-query` flag

支持 8 种参数组合对照（rerank × dedup × multi_query）。

## 四、坦诚评估

### 哪些有效

✅ **规划域 +7.7pp**：BGE-M3 在规划规范上的语义偏最严重，"配建/服务半径/居住街坊"这类术语经过 LLM 扩展后命中率显著提升。

✅ **显性事实 +5.6pp**：直接事实查询是 multi-query 的甜区——LLM 改写不会偏题。

✅ **冒烟改写质量优秀**：3 个示例 in-context 引导有效，3 个变体精准对应 3 个视角。

### 哪些无效

❌ **综合域 0% → 0%**：用户查"北京地区幼儿园服务半径与国标差异"，DB11/1224-2023 这个北京地标根本不在库——再多变体也救不了。这是评测集与规范库的结构性错位（W3 D1 已识别 16/38 条属此类）。

❌ **对抗样本 0%、可解释推理 0%**：这两类需要 LLM 端能力（识别陷阱 / 跨条款推理），不是检索层能解决的。

❌ **strict Hit@5 0pp**：BGE-M3 拉准了召回域，但 reranker 在 top-5 之内没把 expected_clause 排上来。**strict 的瓶颈在 reranker 排序质量，不在召回**。

### 工程债

⚠️ **时延翻倍（3.4s → 6.8s）**：
- 多 query 改写 +1s
- 4 路 embed + search +2s
- RRF/dedup 开销 +0.4s

评测 6.8s/条 ≠ 端到端 TTFT，但前者反映了召回+精排总耗时。**实际生产 TTFT 预估 ~5-6s（LLM 改写 1s + 多 query 1s + 主 LLM 首字 3-4s），擦边 CLAUDE.md 3s SLA**。

W3 D3 需要做的优化：
1. **改写并发化**（用 asyncio 并发 4 路 embed/search，假设切换 Qdrant Docker 后无锁问题）
2. **改写按需触发**（先用单 query 跑，发现召回 score 阈值低再触发多 query）
3. **缓存常见改写**（同义 query 复用结果）

## 六、AIPM 启示（W3 D2 收获）

### 启示 17 · "正确归因" 比 "总体涨多少" 更重要

总体 +2.6pp 看着不亮眼，但拆开看：
- 规划 +7.7pp 是真实大改善
- 综合 0pp 是"病在别处"（评测集 / 规范库不全）
- 对抗 0pp 是"病在别处"（LLM 推理能力，非检索）

**如果只看总体，会下错结论"multi-query 没用"**。

AIPM 视角：**任何评测结果都要拆分维度看**，找出"被平均掉的真实效果"。

### 启示 18 · 不要为难"病在别处"的指标

综合域 0% 和对抗 0%，无论怎么折腾检索都不会涨。**正确做法是承认这些是别的层级的问题，标注好，不要花时间在错误层级**。

### 启示 19 · 工程债要立刻记账，不要"以后再说"

时延翻倍 6.8s 是真问题。如果不立刻在日志里 + 设计文档里标记 "W3 D3 必须做并发/按需触发"，下周很可能忘掉。

**写在 6 个地方**（CLAUDE.md / 设计文档 / 日志 / Task / commit message / TODO 注释）确保不丢。

### 启示 20 · LLM 改写效果跟 prompt 示例质量强相关

3 个 in-context 示例直接定型了 3 个固定视角输出。如果示例混乱，输出会发散偏题。

**做 prompt 时的"示例工程"** 比"指令工程"更关键——示例是 LLM 真正学习的范式。
