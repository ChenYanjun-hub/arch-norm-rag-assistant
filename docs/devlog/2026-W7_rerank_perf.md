# W7 · 分解路径提速：长度分桶 — 启示 92

**结论**：⭐ 目标是让发散题降到核验预算内。**先 profile 再动手**——发现 rerank 占分解路径 **96%**，
embed/search 加起来不到 5%（所以"并行子检索"这个直觉方案是白做）。
继续追下去，"MPS 上批越大越慢"这个反常识现象暴露了真根因：**batch padding 浪费**。
用**长度分桶**（按 passage 长度排序后分批）：80 pairs **11.41s → 5.08s（-55%）**，
且分数**逐项完全一致**（差异 0.000000）——零质量代价。
发散题 13.7s → **11.1s**，核验从「被跳过」变成「跑了」，当场又抓到红线违规。
沉淀 **启示 92**（反常识的测量结果往往指向真瓶颈）。

## 一、先 profile：直觉方案是错的

分解路径（4 子问题）分段计时：

| 阶段 | 耗时 | 占比 |
|---|---|---|
| embed | 0.59s | 4% |
| search | 0.06s | 0% |
| **rerank** | **14.46s** | **96%** |

我原本打算"并行子检索"——**profile 证明那是白做**（embed 批量化只省 0.5s，search 可忽略，
而 Qdrant 本地文件模式本来也不能并发）。**优化必须打在 rerank 上。**

## 二、用数据否掉两个看似合理的方案

**① 减少候选数（20→10）**：每子问题最终只取 2 条，用 20 候选选 2 条看着浪费。
但实测 8 个子问题：**3/8（37.5%）选中结果被换掉**，且换掉的更差——
如「城市道路绿化种植要求」原本选中 CJJ/T75 表3.0.8（栽植土壤质量表），10 候选时丢了它。
→ **不安全，放弃**（这是"性能换质量"，不是纯优化）。

**② 调大 batch size**：GPU 常识是大批更快。实测**恰好相反**：

| 20 pairs | 耗时 |
|---|---|
| bs=1 | 3.05s |
| **bs=2** | **1.98s** |
| bs=4 | 2.04s |
| bs=8（当时默认）| 2.84s |
| bs=40 | 3.76s |

> 插曲：第一次测"批大小无影响"（8/16/32/64 全是 2.8s）——因为
> `_compute_scores(batch_size=BATCH_SIZE)` 是**默认参数，定义时绑定**，
> 改模块属性不生效。**差点据此得出"批大小无关"的错误结论**，改为显式传参才测出真相。

## 三、追根因 → 得到零代价优化

"批越大越慢"违反常识，说明有别的机制在主导。根因是 **`padding=True` 把整批补齐到该批最长序列**：
规范 chunk 长短悬殊（几十字到 800 字），长短混批时短序列白算大量 padding；批越大，混入长序列的概率越高。

**方案：长度分桶** —— 按 passage 长度排序后分批，算完还原原序。

| 80 pairs（分解路径负载）| 耗时 |
|---|---|
| 原样 bs=8（优化前）| **11.41s** |
| 原样 bs=2 | 6.46s |
| **长度分桶 bs=4** | **5.08s** |
| 长度分桶 bs=8 | 5.24s |

**分数逐项差异 = 0.000000** —— 纯性能改动，无语义风险（分桶只改计算顺序，还原原序后完全等价）。

## 四、🎯 端到端效果：提速换来了红线覆盖率

| 场景 | 优化前 引用/总 | 优化后 引用/总 | 核验 |
|---|---|---|---|
| 简单题 | 3.6s / 6.0s | **2.4s / 3.8s** | ✅ |
| **发散题** | 12.6s / **13.7s** | **8.5s / 11.1s** | **⏭跳过 → ✅跑了** |
| 复合题 | — | 4.5s / 6.7s | ✅ |

普通路径 rerank 也从 2.84s → **1.48s（-48%）**，全站受益。

**最有价值的是这个因果链**：提速 → 发散题进入 12s 核验预算 → 核验真的跑了 →
**当场又抓到红线 3 违规**（"**不应**把裸灯设置在视平线上"被写成"**应把**"）。
性能优化直接换来了红线防护覆盖率。

## 五、顺带修掉 verifier 的一个盲区（假告警）

发散题核验跑起来后，日志里出现一类可疑告警：*"未提及该条为强制性条文"*。
查下来是 verifier 的**盲区**：`_build_chunks_block` 只喂了 chunk **正文**，
而"强制性"来自 `is_mandatory` **元数据**、页码来自 `page_start`。
所以答案正确标注"（强制性条文）"反而被判成"片段中无据"——**用户可见的假告警，会摧毁徽章的可信度**。

修法：把 `is_mandatory` / 页码一起写进片段块。修后复测同一查询：
3 条假告警消失，报出的 3 条全是真问题，其中 **2 条是红线 3 违规**：
- 「防火分区最大允许建筑面积**应大于**1500m²」← 原文「**不应大于**」，**语义反转**
- 「**应**扩大至3000m²」← 原文「**可以**增加1.0倍」，强制性用语不符

118 项测试通过（+2 条元数据单测）。

## 六、🎓 启示 92 · 反常识的测量结果往往指向真瓶颈 ⭐

"批越大越慢"违反 GPU 常识。我本可以耸耸肩说"MPS 就这样"，然后接受 bs=2 的小改进。
**追问"为什么"才找到 padding 这个真根因**——而找到根因后，拿到的是**零代价的分桶优化（-55%）**，
而不是"性能换质量"的取舍（减候选那种）。

**对 AIPM 转行的启示**：
- **先 profile 再优化**。我的直觉方案（并行子检索）打在只占 4% 的环节上，profile 一测就知道白做。
- **反常识的数据不要绕过**：它通常不是"平台怪癖"，而是你还没理解的机制。
  理解了机制，往往能拿到"不需要取舍"的优化。
- **区分"纯优化"和"性能换质量"**：分桶是前者（分数 0 差异），减候选是后者（37.5% 选中结果变差）。
  **两者不能混在一个 PR 里报"提速 70%"**——那是在用质量损失冒充性能收益。
- 附带教训：测性能前先确认**参数真的生效**（默认参数绑定坑），否则会得出"改了没用"的假结论。
