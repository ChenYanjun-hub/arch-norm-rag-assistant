## 一、动机

评测口径升级后（v7 strict 89.8%），剩 14 条 strict-miss，其中"真检索可优化"的只剩 ~4 条：
- Q011 防烟楼梯间、Q132 景观设施（真检索失败）
- Q005 绿地率下限、Q030 无障碍类型（"地标挤国标"）

原假设：Q005/Q030 是"地标 DB5301 挤掉国标"的**重排排序问题**，可用确定性"国标优先 boost"修。
动手前先做防回归检查（语料仅 3 部地标、评测无任一题答案是地标 → boost 安全），再诊断根因。

## 三、🎯 关键发现：boost 救不了没召回的

**原计划的"国标优先重排 boost"彻底无效**——Q005/Q030 的国标条根本不在候选集
（深排第 47 / 93 名），**重排 boost 无法 boost 一个不在候选里的东西**。
若不诊断直接写 boost，会白费力气还可能引入回归。

残余 4 条的正确归宿（都不是检索代码）：
- **Q005** → 国标绿地率表 OCR 乱码 → 数据修复线（已归入 OCR 缺陷清单 P1）
- **Q132** → embedding 召回盲区 → BGE-M3 已锁定，记为已知局限
- **Q030** → GB55031 5.1 非干净答案 → 评测 GT 复核
- **Q011** → reranker 相邻条分辨力上限（黑盒）→ 已知局限

**决策：不动检索代码。** 加大候选池（config 早证 -2.6pp 且救不了乱码表）、动 reranker（黑盒）
都低价值高风险；国标 boost 无效。**检索本身已达当前数据/模型下的有效上限。**

## 四、🎓 启示 81 · 召回失败 vs 重排失败，必须分开诊断 ⭐

**"检索没排上"有两种根本不同的病因，解法完全相反：**
- **重排失败**：目标在候选集里，但被重排挤下去 → 调 rerank / boost / 候选格式有救。
- **召回失败**：目标压根没进候选集 → 调重排全是白搭，得动 embedding / query 改写 / 数据质量。

**诊断方法**：追踪目标 chunk 在「粗排 top-K → 重排 top-K → 深排全库」的位置，一眼分辨。

**对 AIPM 转行的启示**：
- **"优化检索"是个太粗的说法**。先定位是召回层还是重排层——**打错层，方案再漂亮也没用**（boost 救不了没召回的）。
- **"知道何时不优化"是判断力**。这一层最有价值的产出是"不改"——诊断证明了没有安全高价值的检索杠杆，
  残余是数据/模型/GT 问题。硬写一个 boost 去凑，是"为了显得在优化而优化"。
- 面试金句：**"我准备做国标优先重排，但诊断发现国标根本没被召回——boost 救不了不在候选里的东西。
  于是我没写那行代码，把问题正确路由给了数据修复和评测复核。"** 这比"我加了个 rerank boost"更能证明工程判断。
