# V2 Day 5 · 规范分类展开 + 点选限定导航 · 启示 76

**日期**：2026-06-16（V2 D5）
**分支**：main
**主题**：侧栏"规范分类"可展开列出收录规范（名+号+状态），点某部→只查这部
**结论**：⭐ 全链路落地并实测通过；本质是**接通一个早已铺好却没接 UI 的潜在能力**（spec_code 过滤）

---

## 一、需求与形态（经确认）

"公开展示已收录规范"——确认面向**用户的覆盖 + 导航面板**（非对外营销页）：侧栏分类展开列出该域规范，点击某部即**限定只查这部**。比纯展示价值高，因为它把"展示"变"导航/限定"。

## 二、关键发现：能力是现成的，只差接线

- `spec_code` 过滤**早已端到端铺好**：`ChatRequest.spec_code`（schema）→ `chatStore.send(opts.spec_code)`（store）→ `run_rag_sync(spec_code_filter=…)`（后端检索）。**但没有任何 UI 接它**——InputBar 的"@ 引用条文"还是个 disabled 路线图占位。
- 所以本功能 80% 是"连点成线"：让侧栏点选去喂那个现成的 spec_code。
- `spec_name` 取自入库元数据、**干净**（OCR 损伤在正文/章节，不在规范名）——抽查 8 部全无残字，可直接展示。

## 三、实现（7 文件）

**后端**
- `schemas.py`：+`SpecBrief{spec_code,spec_name,status}`；`DomainStat +specs[]`
- `stats.py`：聚合时记 spec_name + 复用 `get_spec_status` → 一次 `/api/stats` 拿全（含状态）

**前端**
- `types/chat.ts`：+`SpecBrief`、`DomainStat.specs`
- `Sidebar.tsx`：域行可展开（caret 旋转）→ 列规范行（状态点 + 名省略 + 标准号）；点规范→`onSelectSpec`；激活高亮
- `Chat.tsx`：`specFilter` 态；`handleSubmit` 带 `spec_code`；接 Sidebar/InputBar
- `InputBar.tsx`：限定时顶部显 chip"只查《X》✕"+ placeholder 改"在《X》内提问"
- `design.css`：caret / spec-list / spec-row / filter-chip 样式

## 四、🎯 实测（preview + 后端 curl 双验）

- 展开规划 → 29 部规范行（干净名 + 号 + 绿色现行点）✅
- 点"城市规划数据标准"→ chip + 高亮 + placeholder 变化；**fetch 拦截确认请求带 `spec_code:"CJJ/T 199-2013"`** ✅
- 限定 GB 50180-2018 问幼儿园 → **右栏引用只剩 GB 50180-2018**（后端 curl 对照：带过滤=只 1 部 / 不带=4 部）✅
- 清除限定 → chip/高亮消失，恢复全库 ✅
- tsc 通过 · 无 console error
- 排查花絮：UI 一度显示多部引用，经"后端 curl 直验 + 等面板 settle 重读"判定为**读取时机/旧轮残留**的测试假象，非过滤失效（与启示 68/73 同：UI 自动化要和权威层交叉验证）

## 五、🎓 启示 76 · 最高 ROI 的功能常是"接通早已铺好却没接 UI 的潜在能力" ⭐

`spec_code` 过滤的 schema、store、后端检索**三层都现成**，只是从来没有 UI 去喂它——"@ 引用条文"还是个永远 disabled 的占位。这次新功能 80% 的工作是**连点成线**，几乎没碰核心逻辑。

**对 AIPM 转行的启示**：
- **动工前先盘"潜在能力"**：很多看似"新功能"的需求，底层能力其实早建好（为别的目的、或半途搁置），只差最后一截接线。先 grep/读代码盘一遍 `spec_code`/`filter`/`session_id` 这类"通了一半"的参数，能省掉大量重复造轮子。
- **占位 ≠ 能力缺失**：disabled 的"@ 引用条文"让人以为"按规范限定"没做，实则后端早能做。**别被前端占位误导**对能力边界的判断（与启示 75「占位埋假设」同源）。
- **识别这种"连线型"高 ROI 功能，是 PM 的价值点**：投入小、风险低（不动核心）、用户价值直接——优先级该往前排。
