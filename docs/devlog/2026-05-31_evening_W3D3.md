# W3 Day 3 · Hybrid 检索（BM25 + 向量）实验 —— 失败结论

**日期**：2026-05-31（周日晚场）
**阶段**：W3 D3
**主题**：BM25 + 向量 RRF 融合，预期补 BGE-M3 在专业术语精确匹配的弱项
**结论**：❌ 在当前评测集上 **-2.6pp 负优化**，默认关 hybrid，保留代码

---

## 一、起因

W3 D2 多 query 改写让 Hit@5 loose 涨到 50.0%，但仍有 50% miss。设计文档原假设：
- BGE-M3 语义偏 → 加 BM25 短语精确匹配能补全

**典型预期 case**：
```
Q009 "高层民用建筑分类标准？" → expected GB 55037-2022 5.1.1
BM25 对 "高层民用建筑" "分类" 关键词应能精确召回
```

---

## 二、做了什么

### 1. 装依赖 + 写 BM25 索引器
- 装 `rank_bm25` (0.5MB) + `jieba` (中文分词)
- 新建 `app/rag/bm25_indexer.py`：扫 `chunks/*.json` → jieba 分词 → 内存 BM25Okapi
- 启动时 lazy build，4773 chunks 索引耗时 832ms
- 单例 + 进程内常驻

### 2. pipeline.py 接入 hybrid
- 加 `HYBRID_ENABLED` env flag
- 每路 query 同时走 vector search + BM25 search → 全部用 `rrf_fuse` 融合
- 失败降级仅向量

### 3. 评测对照（2 次实验都失败）

#### 实验 v1：BM25 跟所有 query 变体走（8 路融合）

| 指标 | W3 D2 (hyb=OFF) | W3 D3 v1 | Δ |
|---|---|---|---|
| Hit@5 loose | **50.0%** | 47.4% | **❌ -2.6pp** |
| 规划域 | 61.5% | 53.8% | **❌ -7.7pp** |
| 显性事实 | 72.2% | 66.7% | **❌ -5.6pp** |

#### 实验 v2：BM25 只跟原 query 走 1 路（权重降到 20%）

| 指标 | W3 D3 v1 (hyb=full) | W3 D3 v2 (hyb=20%) | Δ |
|---|---|---|---|
| Hit@5 loose | 47.4% | **47.4%** | 0 |

**降权完全没用**——结果跟全权一模一样，证明 BM25 的"负作用"主要来自原 query 那 1 路本身，不是变体污染。

---

## 三、失败根因（数据驱动诊断）

定位"哪条 query 被 BM25 弄丢了"：

```
Q021 "我们小区规划了 280m 服务半径的 8 班幼儿园 符合国标吗？"
  期望: GB 50180-2018 表 5.0.3
  hyb=OFF: rank_loose=3 (top-5 命中 GB 50180-2018) ✅
  hyb=ON:  rank_loose=None (整个掉出 top-20)       ❌
```

**根因分析**：

1. Q021 是"问具体数值是否合规"型查询（含 "280m" "8 班" 等具体数字）
2. BM25 召回了大量含 "280m" / "幼儿园" / "8 班" 的**非答案条款**（散落在各种规范的解释条文里）
3. 这些 BM25 高分但无关的条款填满了 top-20 的 RRF 累加分
4. BGE-M3 路径里的 GB 50180-2018 表 5.0.3（**真正答案上限规定，不含具体 280m**）被挤出 top-20

**核心结构性问题**：

| 检索类型 | 适合 | 不适合 |
|---|---|---|
| 语义检索（BGE-M3）| "含义相关"：用户问 280m 是否合规 → 答案是上限规定 | 专业术语精确匹配 |
| 词袋检索（BM25）| "用词相同"：用户问"耐火等级" → 答案也含"耐火等级" | 用户的查询用词跟答案条款不重合 |

**我们的 v2 评测集大量是"问具体数值是否合规"型**，BGE-M3 + 多 query 改写已经能很好捕捉这类语义关联。BM25 反而是干扰。

## 四、AIPM 启示（W3 D3 收获最多）

### 启示 21 · "改了反而劣化"是更宝贵的成果

W3 D1 的 dedup 学到 "改了不涨"，今天进一步：
- 不是所有"业界经典方法"都适合自己的场景
- BM25 在通用 RAG 文献里"必加"，但在 **"问数值是否合规"型评测集 + 规范条文**上是负优化
- **场景适配 > 技术先进性**

### 启示 22 · 数据驱动决策的极端版本

如果按"经验/直觉"做产品决策：
- "我们应该加 BM25，因为大家都加" → 上线后真实用户问"280m 合规吗"，召回质量下降，没人知道是 BM25 干的
- "需要 hybrid 搜索" → 半年后某个用户投诉，复盘才发现是融合策略错

**评测体系跑通后，做任何"业界建议优化"都先量化**——15 分钟评测能省你 6 个月的回滚成本。

### 启示 23 · 失败要诚实记录，不要藏

工程师常犯的错：
- "嗯，BM25 我试了但效果不好，删了不提"
- 半年后另一个工程师又想到"应该加 BM25"，又试一遍

**今天日志写明"为什么 BM25 在我们这里失败"，比单纯关掉它价值大 10 倍**。

### 启示 24 · "保留代码 + 默认关 + 文档解释" 是正确处置

不要：
- ❌ 删 bm25_indexer.py 整段（下次想试需要重写）
- ❌ 留默认开（拖累生产）

要：
- ✅ env flag 默认 false（保 SLA）
- ✅ 代码完整保留（含 RRF 融合）
- ✅ config.py 注释解释为什么默认关 + 哪种场景可能有效
- ✅ 日志详细分析失败原因

下次如果数据集 / 业务场景变化（如做"专业术语精确匹配"型 query 多的产品），翻 flag 即可重新试。
