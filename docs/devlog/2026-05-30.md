## 二、决策与权衡

### 决策 1：Reranker 兼容性 — 绕开 FlagEmbedding

**问题**：
- transformers 5.9.0 移除了 `XLMRobertaTokenizer.prepare_for_model`
- FlagEmbedding 1.4.0（最新）内部仍在调这个老 API
- 每次 rerank 调用都崩 → fallback 到 vector top-k → **形同摆设**

**3 个候选方案**：

| 方案 | 工时 | 长期成本 |
|---|---|---|
| 降级 transformers 到 4.x | 30min | 影响 BGE-M3 embedder，风险大 |
| 等 FlagEmbedding 1.5 | 不确定 | 受上游维护节奏摆布 |
| **自包 transformers AutoModelForSequenceClassification**（✅ 选）| 1h | 摆脱上游延迟，长期免维护 |

**实现**：30 行代码，单例 `(tokenizer, model, device)`，自动选 MPS / CUDA / CPU。

### 决策 2：评测集与规范库错位 — 改评测集（v2）

**问题**：评测集 v1 预设的 expected_spec 是 2010-2019 老国标，但**实际入库**主要是 2021-2024 强制性通用规范（GB 55xxx）。20 条小样本 strict Hit@5 = 5% 触发警报。

**3 个候选方案**：

| 方案 | 选了否 |
|---|---|
| 改评测集（让 expected 匹配真实数据资产）| ✅ |
| 扩规范库（补 6-8 部缺失 PDF + ingest）| ❌ 需用户提供文件，W1 已知 3 部无法入库 |
| 加 spec_alias 等价映射 | ❌ 等价性主观，可信度低 |

**v2 实现**（`build_eval_v2.py`）：
- `GB 50016-2014` → `GB 55037-2022`（防火）
- `GB 50352-2019` → `GB 55031-2022`（民建通用）
- `GB 50096-2011` → `GB 50368-2005`（住宅）
- 5 条无替代 → `expected_spec` 置空（评测跳过，保留可追溯标记）

结果：**kept 27 / remapped 11 / dropped 12 / 可评 38**。

### 决策 3：retrieval SSE 事件报告"真实状态"而非"flag"

**之前**：`{"reranked": RERANK_ENABLED}` — flag 是 true 但实际 fallback 了，**前端会被误导**
**之后**：`{"reranked": rerank_used}` — 反映本次是否真正成功 rerank

符合 CLAUDE.md 红线"不能假报状态"。

## 四、踩坑与诊断

### 坑 1 · Reranker 首次成功加载但每次调用都崩

- 错误：`XLMRobertaTokenizer has no attribute prepare_for_model`
- 排查：`transformers=5.9.0` × `FlagEmbedding=1.4.0`
- 验证：用原生 `AutoModelForSequenceClassification` + `tokenizer(query, passage)` → sigmoid，**1 对 score = 0.9262，完美**
- 修复：重写 `reranker.py` 30 行
- 教训：**第三方封装库可能拖累上游升级，关键模型直接用 transformers 原生 API**

### 坑 2 · Qdrant 本地文件锁

- 评测脚本启动时报：`Storage folder already accessed by another instance`
- 原因：backend uvicorn 持有 Qdrant 文件锁，第二个进程进不去
- 临时方案：评测期间 `pkill uvicorn` → 跑评测 → 重启 backend
- 长期方案：W3 切 Qdrant Docker 服务（CLAUDE.md "已知限制"已记录）

### 坑 3 · Q005 "绿地率"诊断

- 期望 `GB 50180-2018 4.0.4`，top1 是 `DB 5301:T 21-2019`
- 直接 grep chunks JSON：**没有 `4.0.4`，但有 `表40.3`**
- 真相：**OCR 把 `表4.0.3` 识别成 `表40.3`**（小数点被吞）
- 检索本身做对了（GB 50180 表4.0 在 top-14、表40.3 在 top-18 都召回了），是 OCR 上游污染
- 教训：**评测出错时先看 chunks，再怪检索**

### 坑 4 · 评测集与规范库错位（最大教训）

- 评测集是准备日做的，预设 expected 是当时心目中的"标准规范清单"
- ingest 实际入库的是用户日常使用的规范（GB 55xxx 系列偏多）
- 结果：**20 小样本 strict Hit@5 = 5%，第一反应是检索弱，实际是评测集本身错位**
- 教训：**评测集和数据资产是一体两面，每次 ingest 后必须 reconcile**

## 七、AIPM 洞察（按帮助度排，对应 v3.0 文档将更新到 v3.1）

### 洞察 14 · "5% Hit Rate" 是评测的第一课

数字本身没意义，**"为什么是 5%"才有意义**。如果不停下来诊断就盲改检索器，会越改越偏。

**AIPM 用例**：当评测数字异常，**先确认评测集和数据资产是否一致**（错位率 22%），再考虑算法。否则就是在错误的方向上做对的事。

### 洞察 15 · 测什么 = 工具决定能力的边界

评测集 v1 在准备日就做完了，但今天才发现它"问对了问题但定错了答案"。这与代码无关，与"AIPM 是否真实使用过自己的系统"有关。

**反例**：W1 时若先跑通端到端，再让 AIPM 用自己的产品提问一周，会更早发现这些问题。

### 洞察 16 · 数据集 ↔ 系统 必须周周对账

错位发生在 (评测集设计时心目中的清单) ≠ (ingest 实际入库的清单)。两份清单从未交叉过，直到今天才碰头。

**AIPM 制度建议**：每周末跑一次 `inventory_diff`，列出"评测集期望但库里没有的规范" + "库里有但评测集没覆盖的规范"，强制 reconcile。

### 洞察 17 · 指标双轨制（strict + loose）

- strict 看精度，loose 看召回
- 当 **strict ≪ loose**（如今天 2.6% vs 47.4%）→ OCR / 分块 / 编号精度问题
- 当 **strict ≈ loose** → 召回质量问题
- 两个数字一起看才能定位问题层次

### 洞察 18 · Reranker 价值必须用数字证明

加 reranker 之前的直觉是"提升 20%"，今天实测整体 +2.7pp、规划域 +7.6pp、消防域 0pp（已饱和）、综合题 0pp（无能为力）。

**AIPM 用例**：没有评测就无法判断"哪些动作真的有用"。是否值得花一天工程化的依据，只能是数字。
