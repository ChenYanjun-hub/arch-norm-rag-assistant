# W7 · Agent Router 智能调度 + Agent 行为评测 — 启示 87

**结论**：⭐ 三个 agent 此前**全部默认关**——因为每个都对**每条** query 无差别收 LLM 税。
加一层**廉价规则路由**（48 条 query 共 0.2ms、零 LLM 成本）决定每条 query 走哪条路，
让 agent 从"实验室 flag"变成"可默认开的生产能力"。
同时补上 **agent 行为评测**（此前只有检索/生成/兜底三层评测，唯独没有"agent 决策对不对"）。
路由准确率 **93.8%（clear 样本 100%、漏触发 0%）**。沉淀 **启示 87**（agent 的瓶颈常在调度，不在能力）。

---

## 一、真问题：能力做出来了，但没人敢开

查询分解、引用核验、工具调用三个 agent 都已生产化，但 config 里全是 `default=false`。
原因不是效果不好，是**成本模型不对**：每个 agent 都对**所有** query 加一次 LLM 调用
（分解判定 ~1.5s、核验 ~1.3s），而真实流量里多数是简单单点查询，根本用不上，
还会压 TTFT ≤3s 的 SLA。

**这不是"agent 能力不够"，是"缺一层调度"。** 主流大厂 agent 架构里，
Router/Orchestrator 就是这一层——先廉价判断意图，再决定是否付昂贵的推理成本。

## 二、方案：规则打确定区，LLM 只兜模糊区

- `services/agent_router.py`：纯正则路由（复用 `scenario.py` 同款思路，~0ms、零成本）
  - `tool`：目录导航 / 规范号+条文号 / 规范号+状态问法
  - `decompose`：并列复合（和/与/顿号 + 要求/因素/区别）、发散（有什么/哪些要求）
  - `plain`：兜底（默认）
- 关键取舍两条（都由评测数据逼出来的，不是拍脑袋）：
  1. **复合优先于指标守卫**："消防车道净宽和净高要求"含具体指标词，但并列结构是强信号 → 仍拆。
  2. **具体指标名词判单点**："填方路基对填料的最大粒径有什么要求"措辞像发散，
     但落在一个具体量上 → 判 plain（治误触发）。
- `resolve_route(allow_llm=True)`：只对规则分不开的模糊区升级到 LLM 判定（默认关）。
- `pipeline.py`：路由结果统一 gate 三个 agent；router 关闭时退回旧行为（向后兼容）。

## 三、🎯 Agent 行为评测（补上第四层评测）

此前评测覆盖：检索层（run_eval）、生成层（run_quality_eval）、兜底（run_fallback_eval）——
**唯独没有评 agent 自己的决策**。新建：

- `data/eval/agent_route_set_v1.csv`：48 条手工标注（tool 12 / decompose 14 / plain 22），
  其中 **10 条 borderline**（"措辞像发散实为单点"），专测误触发抵抗力。
  `plain` 样本取自真实评测集，不是顺手编的。
- `scripts/run_agent_eval.py`：准确率（整体/clear/borderline）、每类 P/R、
  **误触发率**（该 plain 却调 agent = 白付成本）、**漏触发率**（该 agent 却退 plain = 无损降级）、混淆矩阵。

**标注纪律**：ground-truth 按**语义真实**判定，不按"我的正则怎么走"——
否则就重蹈启示 78（优化一个坏掉的 KPI）。边界样本单独标 `borderline`，分开报告。

### 结果演进（两轮，均为有原则的修正而非针对样本打补丁）

| | 整体 | clear | borderline | 误触发 | 漏触发 |
|---|---|---|---|---|---|
| 初版规则 | 77.1% | 92.1% | 20.0% | 27.3% | 19.2% |
| +复合覆盖 +指标守卫 | 91.7% | 97.4% | 70.0% | 13.6% | 3.8% |
| **+长名词窗口放宽（终版）** | **93.8%** | **100%** | 70.0% | 13.6% | **0%** |
| 终版 + LLM 兜模糊区 | 95.8% | 97.4% | 90.0% | 4.5% | 3.8% |

`tool` 路由全程 **100% 召回 / 100% 精确**——规范号 + 条文号/状态问法是极强信号。

## 四、决策：LLM 升级默认关（用数据决定，不用"看起来更强"决定）

LLM 兜模糊区确实把误触发从 13.6% 降到 4.5%，但代价是：
- **clear 样本从 100% 掉到 97.4%**（LLM 把"城市地下道路设计要满足哪些基本要求"判成了单点）
- 引入不确定性 + 10% 的 query 要付 ~0.8s

而纯规则版：**clear 100%、漏触发 0%、0ms、确定性、可单测**。
剩下的 3 条误触发全是 borderline 措辞题，**误触发的实际代价只是多花一次分解成本，答案仍然正确**——
比"发散题没拆导致答不全"轻。所以**默认纯规则，LLM 升级留 flag**（成本成为瓶颈时再开）。

## 五、🎓 启示 87 · Agent 的瓶颈常在调度，不在能力 ⭐

**我做完三个 agent 才发现，它们全都默认关着——不是因为不好用，是因为没有调度层，
只能"要么全开（每条 query 都付税）要么全关"。**

**对 AIPM 转行的启示**：
- **能力 ≠ 可上线**。一个 agent 能不能默认开，取决于"**它对不该用它的 query 收多少税**"。
  Router 的价值不是提升单条答案质量，是**让已有能力的成本变得可承受**。
- **调度层要廉价**。用正则/规则先分掉 90% 的确定情况，LLM 只碰真正模糊的那 10%——
  这是大厂 agent 的标准做法（cheap classifier + LLM fallback），也是我用数据验证过的边界。
- **给 agent 建评测，和给模型建评测一样重要**。我原本有检索/生成/兜底三层评测，
  却没有一层在问"agent 的决策对不对"。没有它，router 的规则就只能靠感觉调。
  **误触发率/漏触发率这类指标，是 agent 时代 PM 该定义的新 KPI。**
