# 执行摘要 Executive Summary

## 一、产品概览
建景规规范助手是一款面向设计院规划师的 AI 智能规范查询工具。基于 RAG 技术架构，覆盖规划、建筑、景观、消防、结构 5 类核心规范（共约 35 部国标+地标），提供严谨权威、可溯源跳转的智能问答能力，定位类似"AI 版规范法条数据库"，而非通用聊天伙伴。

## 二、解决的核心问题
设计院规划师在日常工作中每天平均花费 1-2 小时查询规范，但当前方式存在 3 类痛点：
- **查不到**：关键词搜索能力弱、跨规范查询难
- **看不懂**：条文晦涩、强制性识别不清
- **不敢用**：通用 LLM 易编造，无法验证

本产品通过 AI 智能问答 + 精确到条文级的引用溯源，让规范查询效率提升 5-10 倍。

## 三、产品差异化
> 市场上同时具备"规范权威性 × AI 智能化 × 可溯源"三者的产品空白，本项目瞄准这个空白。

| 维度 | 通用 LLM | 规范电子版 | **本产品** |
|---|---|---|---|
| AI 智能问答 | ✓ | ✗ | ✓ |
| 规范权威性 | ✗（易编造） | ✓ | ✓ |
| 可溯源跳转 | ✗ | 部分 | ✓✓ |

## 四、核心方案
- **理想态定义**：5 大维度框架 + 6 场景 Golden Sample + 8 条风格红线 + 8 类边界兜底
- **功能架构**：5 大功能域 / 18 个模块（MVP 11 个 + V2/V3 7 个）
- **评测体系**：生成层 7 维度 MOS（含 2 项一票否决）+ 检索层 6 指标 + 250 条评测集 + 性能 3 维度
- **目标客户**：中型综合设计院（500 人以上规模），MVP 阶段先做个人版验证核心价值

## 五、关键验收指标

| 类别 | 指标 | MVP 目标 |
|---|---|---|
| 质量 | 评测体系综合得分 | ≥ 75 分 |
| 质量 | 一票否决项触发数 | 0 |
| 性能 | TTFT P95 | ≤ 3s |
| 性能 | 总响应时长 P95 | ≤ 15s |
| 检索 | Hit Rate@5 | ≥ 90% |
| 稳定 | 可用性 SLA | ≥ 99% |

## 六、MVP 范围与边界
- ✅ **做**：11 个核心模块覆盖问答主流程、引用溯源、原文跳转、边界兜底
- 🔶 **V2 做**：多轮对话、对话历史、PDF 文件上传解读、智能追问推荐
- 🔶 **V3 做**：企业版（SSO、权限、协作）、规范库扩展、付费功能
- ❌ **不做**：账号体系、付费、协作、图纸识别、其他专业规范

# 第一部分 · 理想态定义

## 一、理想态定义的整体框架

5 大维度体系化构建：

| 维度 | 核心问题 |
|---|---|
| ① 用户画像 | 是谁在用？专业度如何？ |
| ② 使用场景 | 在什么场景下用？解决什么任务？ |
| ③ 输入定义 | 用户的 query 长什么样？ |
| ④ 输出定义 | 理想的回答是什么样？（核心）|
| ⑤ 边界场景 | 不在能力范围时怎么处理？ |

> **核心方法论**：用户 × 场景 交叉矩阵。每个交叉单元格 = 一个具体的理想态样本。

## 二、规划师场景矩阵

### L1 · 核心高频（MVP 必做）· 占比 87%

| 场景 | 典型问句 | 占比 |
|---|---|---|
| ① 规范查找 | "幼儿园服务半径不应大于多少？" | 50% |
| ② 规范确认 | "我做的 XX 是否合规？" | 20% |
| ③ 规范解释 | "五分钟生活圈是什么意思？" | 15% |

### L2 · 复杂推理（V2 迭代）· 占比 13%

| 场景 | 典型问句 | 占比 |
|---|---|---|
| ④ 条文对比 | "国标 vs 北京地标差异？" | 8% |
| ⑤ 计算辅助 | "容积率 2.5 对应多少建面？" | 5% |

### L3 · 边界场景（必须兜底）· 占比 2%

⑥ 边界兜底：查不到 / 规范作废 / 范围外 / 闲聊 / 模糊提问 / 敏感问题 / 超出权限

> **MVP 优先级**：先做 ①②③⑥（覆盖 87% 流量），V2 补 ④，V3 补 ⑤。

## 三、各场景的理想态输出规范

| 场景 | 必备内容 | 长度 | 结构 |
|---|---|---|---|
| ① 规范查找 | 直接答案 + 规范名 + 标准号 + 条文号 + 是否强制 | 简短（50 字内）| 结论先行 + 分层展开 |
| ② 规范确认 | 合规判断（是/否/部分）+ 依据条文 + 风险提示 | 中等（100-200 字）| 判断 → 依据 → 风险 |
| ③ 规范解释 | 准确定义 + 出处 + 关键要点 | 中等（150-300 字）| 定义 → 要点 → 示例 |
| ④ 条文对比 | 对比维度 + 各规范规定 + 优先级 | 中长（表格）| 表格对比 + 适用性 |
| ⑤ 计算辅助 | 公式 + 输入参数 + 分步演算 + 结果 + 出处 | 长（分步）| 公式 → 演算 → 结果 |
| ⑥ 边界兜底 | 明确告知能力边界 + 引导下一步 | 短（30-50 字）| 单一段落 |

## 四、风格红线清单（8 条 · 评测时直接使用）

1. 无寒暄开场（如"好的""根据您的问题"）
2. 无表情符号、无语气助词
3. 数字精确（如"300m"，不用"大约""左右"）
4. 用词正式（用"规范规定"，不用"我觉得""一般来说"）
5. 区分"应/宜/可"，不混用
6. 结论先行，无铺垫
7. 结构清晰（重要信息高亮、可扫读）
8. 涉及设计建议时明确"建议非强制"

## 五、容易被忽略的关键点

1. 引用必须精确到"规范条文号"（如 GB 50180-2018 第 6.4.1 条）
2. 规范有时效性：必须标注版本号、是否现行、是否被替代
3. 强制性条文 vs 一般条文必须明确区分（关乎责任）
4. 地方规范与国标冲突时的优先级表达
5. "设计建议"场景必须明确"建议非强制"，避免越权
6. 涉及计算（如容积率、退线）必须给出公式 + 出处
7. 不确定时的话术统一（"未查询到..."而非编造）

## 六、6 个场景的 Golden Sample 设计要点

### Golden Sample ① 规范查找
- **用户输入**："居住区配套幼儿园的服务半径不应大于多少米？"
- **理想输出结构**：
  - 蓝色高亮结论框：「不应大于 300 米」
  - 规范依据卡片：GB 50180-2018 + 表 5.0.3 + 跳转链接 + 强制性标签
  - 原文摘引（衬线字体）
  - 智能追问按钮
- **设计要点**：结论先行、溯源完整、强制性视觉标识

### Golden Sample ② 规范确认
- **用户输入**："280 米服务半径的 8 班幼儿园，符合国标吗？"
- **理想输出结构**：
  - 绿色合规判断框：「符合国家规范要求」
  - 逐项核查表
  - 黄色风险提示框
- **设计要点**：判断分级（绿/红/黄三色）、逐项核查、风险前置

### Golden Sample ③ 规范解释
- **用户输入**："什么是五分钟生活圈？"
- **理想输出结构**：定义框 + 原文摘引 + 三级生活圈对比表 + 规范依据
- **设计要点**：定义先行用权威原文、不做"通俗化改写"

### Golden Sample ④ 条文对比
- **用户输入**："国标和北京地标对幼儿园服务半径差异？北京项目按哪个执行？"
- **理想输出结构**：执行结论框 + 对比详情表（差异点高亮）+ 执行原则
- **设计要点**：先明确"该执行哪个"、差异点高亮、援引法律

### Golden Sample ⑤ 计算辅助
- **用户输入**："5 公顷用地容积率 2.5，可建多少建筑面积？"
- **理想输出结构**：结果卡片 + 分步演算 + 提示框 + 规范依据
- **设计要点**：结果卡片化、不编造、公式三段式抗幻觉

### Golden Sample ⑥ 边界兜底
- **用户输入**："居住区里宠物友好设施的配建标准是什么？"
- **理想输出结构**：灰色"未查询到"提示框 + 3 个相关方向引导
- **设计要点**：诚实第一原则、提供下一步方向、不编造

## 七、边界兜底场景的 8 个子类清单

| 子类 | 触发条件 | 核心话术 |
|---|---|---|
| 查不到 | 规范库中无相关内容 | "未在现行规范库中查询到..." |
| 规范作废 | 检索到的规范已被新版替代 | "您查询的 XX 已于 YYYY 年废止" |
| 规范冲突 | 多个规范规定不一致 | "国标/地标存在差异，分别为..." |
| 范围外 | 非 5 类规范问题 | "本助手专注于 5 类规范查询..." |
| 闲聊 | 与业务无关的对话 | 简短礼貌回应 + 引导回业务 |
| 模糊提问 | query 缺关键信息 | "请补充：项目所在城市/规范类别..." |
| 敏感问题 | 涉及违规设计、规避审查 | "建议咨询主管部门或专业审图机构" |
| 超出权限 | 涉及具体审批 | "审批权限属规划主管部门..." |

# 第二部分 · 评测体系构建

## 总览

| 模块 | 核心内容 |
|---|---|
| ① 生成层评测 | RAGAS 框架 + 7 维度 MOS 评分体系 |
| ② 检索层评测 | 6 个核心指标 + 三级相关性标注 |
| ③ 评测集构建 | 250 条 query 集 · 三维配比设计 |
| ④ 性能评测 | 3 维度 7 指标 + 监控大盘 |

### RAG 评测的核心分层

```
用户 Query → 检索 Chunks → LLM 生成回答
                ↓             ↓
          检索层评测       生成层评测
```

> **关键认知**：检索没召回 → 生成再好也错；检索召回了 → 生成可能仍出错（幻觉）。必须分层评测。

## 模块一 · 生成层评测

### 7 个维度与权重

| 分组 | 维度 | 权重 | 核心问题 |
|---|---|---|---|
| A · RAGAS | ① 忠实性 Faithfulness | 25% | 答案是否完全基于检索 chunks |
| A · RAGAS | ② 答案相关性 Relevancy | 15% | 答案是否切题 |
| B · 产品 | ③ 引用准确性 | 20% | 规范名/标准号/条文号是否准确 |
| B · 产品 | ④ 完整性 | 15% | 是否包含所有应答要素 |
| B · 产品 | ⑤ 强制性标识准确 | 10% ★ | "应/宜"区分（一票否决）|
| B · 产品 | ⑥ 兜底合规性 | 5% ★ | 查不到时是否诚实告知（一票否决）|
| C · 风格 | ⑦ 风格合规 | 10% | 是否符合 8 条风格红线 |

### 一票否决规则
当 ⑤ 强制性标识 ≤ 1 分 或 ⑥ 兜底合规 = 0 分时，整体降为不合格。

### 总分计算
```
总分 = Σ (单项得分/2 × 权重 × 100)
合格线：≥ 75 分
不合格：< 75 分 或 触发任一一票否决
```

### 7 维度 MOS 评分细则（0/1/2 三分制）

**① 忠实性（权重 25%）**
- 2 分：每个事实陈述都能在 chunks 中找到对应
- 1 分：核心事实正确，但存在轻微延伸推断
- 0 分：chunks 中没有的事实内容（编造）

**② 答案相关性（权重 15%）**
- 2 分：直接命中用户问题核心
- 1 分：回答了问题但有较多无关延展
- 0 分：完全没回答问题

**③ 引用准确性（权重 20%）**
- 2 分：规范全称完整、标准号准确、条文号精确到节
- 1 分：规范名简写或条文号粗略，但信息无错
- 0 分：规范号错误、版本错误、条文号错误、链接失效

**④ 完整性（权重 15%）**

各场景必备要素：

| 场景 | 必备要素清单 |
|---|---|
| 规范查找 | 结论 + 规范名 + 条文号 + 强制性标识 + 原文摘引 |
| 规范确认 | 合规判断 + 逐项核查 + 依据 + 风险提示 |
| 规范解释 | 定义 + 出处 + 关键要点 |
| 条文对比 | 执行结论 + 对比表 + 优先级原则 |
| 计算辅助 | 结果 + 公式 + 分步演算 + 出处 |
| 边界兜底 | 明确告知 + 相关方向 + 能力边界说明 |

**⑤ 强制性标识准确（权重 10% · ★ 一票否决）**

规范用语等级：
- **必须 / 严禁** → 最强约束
- **应 / 不应** → 强制要求
- **宜 / 不宜** → 推荐要求
- **可 / 不可** → 允许选择

评分：
- 2 分：用语精确 + 强制性视觉标识
- 1 分：用语对但无标识
- 0 分（★ 一票否决）：把"宜"擅自升级为"应"

**⑥ 兜底合规性（权重 5% · ★ 一票否决）**
- 2 分：诚实告知 + 相关方向引导
- 1 分：告知到位但无引导
- 0 分（★ 一票否决）：编造规范号或条文

**⑦ 风格合规（权重 10%）**
- 2 分：8 条红线全部符合
- 1 分：违反 1~2 条
- 0 分：违反 3 条及以上

### 评分员对齐机制
每个维度配 5~10 条标注示例。评测员先做 20 条对齐测试，Kappa 系数 ≥ 0.7 才能正式打分。

## 模块二 · 检索层评测

### 检索全链路
```
规范库 → 分块 Chunk → 向量召回（Top-K） → Rerank 精排（Top-N） → 给 LLM
```

### 三个评测层面

| 层面 | 关注问题 | 核心指标 | 评测方法 |
|---|---|---|---|
| A · 分块质量 | "切得好不好？" | 语义完整性、条款独立性 | 人工抽检 |
| B · 召回质量 | "找全没找全？" | Recall@K、Hit Rate@K | 算法自动 |
| C · 排序质量 | "排序对不对？" | MRR、NDCG@K | 算法自动 |

### 6 个核心指标

| 指标 | 公式 | 说明 |
|---|---|---|
| ① Recall@K | Top-K 中相关 chunks / 库中所有相关 chunks | 召回率 |
| ② Precision@K | Top-K 中相关 chunks / K | 精确率 |
| ③ Hit Rate@K | 至少命中一次的 query / 总 query | 业务汇报指标 |
| ④ MRR | 1/N × Σ (1 / 第一个相关结果的排名) | 排序质量 |
| ⑤ NDCG@K | DCG / 理想 DCG | 综合指标 |
| ⑥ Context P/R | RAGAS 框架：句子级粒度 | LLM 自动判断 |

> 所有指标必须带 @K 限定。MVP 阶段重点关注 Recall@5。

### Chunk 相关性三级标注
- **2 分（高度相关）**：chunk 直接包含答案
- **1 分（部分相关）**：提供背景或定义
- **0 分（不相关）**：无主题关联

### 检索层目标值

| 指标 | MVP 目标 | V2 目标 |
|---|---|---|
| Hit Rate@5 | ≥ 90% | ≥ 95% |
| Recall@5 | ≥ 80% | ≥ 90% |
| Precision@5 | ≥ 50% | ≥ 70% |
| MRR | ≥ 0.7 | ≥ 0.85 |
| NDCG@5 | ≥ 0.75 | ≥ 0.88 |

> **关键说明**：优先保 Recall，再调优 Precision。漏掉相关 chunk 比多召几个无关 chunk 危害更大。

### 分块策略评测

| 评测项 | 通过标准 |
|---|---|
| 条款独立性 | ≥ 90% chunk 边界与条款对齐 |
| 语义完整性 | ≥ 95% chunk 语义完整 |
| 跨条款关联 | ≥ 80% 关联引用可追溯 |
| 表格保留率 | 100%（不应切散表格）|

## 模块四 · 性能评测

### 三维框架

| 维度 | 关注问题 | 核心指标 |
|---|---|---|
| A · 速度 | "答得快不快？" | TTFT、总响应时长、吐字速度 |
| B · 压力 | "扛不扛得住？" | QPS、性能衰减拐点 |
| C · 稳定性 | "稳不稳？" | 错误率、可用性 SLA |

### 统计口径：必须用 P95/P99

举例：100 次请求中 99 次 2s，1 次 100s：
- 平均值 = 2.98s（被掩盖）
- P50 = 2s
- P95 = 2s
- **P99 = 100s（真正暴露问题）**

> **结论**：统一使用 P95（主考核）+ P99（告警阈值）

### 7 个核心指标

| 指标 | 定义 | MVP 目标 |
|---|---|---|
| ① TTFT 首字时间 | 发送到首字符的时间 | P95 ≤ 3s · P99 ≤ 5s |
| ② 总响应时长 | 发送到完整回答的时间 | P95 ≤ 15s · P99 ≤ 25s |
| ③ 吐字速度 | 流式每秒 token 数 | ≥ 20 tokens/s |
| ④ 并发上限 QPS | 保证质量的每秒请求数 | ≥ 10 |
| ⑤ 性能衰减拐点 | 性能下降的临界点 | 输出压测报告 |
| ⑥ 错误率 | 错误或超时的占比 | ≤ 1% |
| ⑦ 可用性 SLA | 正常服务时间占比 | ≥ 99.0% |

### MVP 优先级
> 质量 > TTFT > 总时长 > QPS

### 监控大盘 + 告警阈值

| 触发条件 | 告警动作 |
|---|---|
| TTFT P95 > 5s 持续 5min | 钉钉提醒 |
| 错误率 > 3% 持续 5min | 短信告警 |
| 可用性日内跌至 < 99% | 立即告警 + 排查 |

# 第 1 章 · 项目背景

## 1.1 问题陈述
设计院规划师在日常工作中频繁需要查询设计规范，但当前方式存在显著痛点：

| 痛点 | 具体表现 |
|---|---|
| 查询效率低 | 翻阅纸质规范或 PDF，关键词搜索弱，找一个条文需 5-10 分钟 |
| 规范分散 | 国标 + 地方标准 + 各专业规范分散在不同文件 |
| 版本混乱 | 规范频繁更新，工程师常误用已废止版本 |
| 强制性条文易遗漏 | "应/宜"用词差异容易被忽略 |
| 新人成长慢 | 初级设计师对规范体系不熟悉 |
| 现有 AI 工具不可信 | 通用 LLM 容易编造条文号、虚构数据 |

## 1.2 市场机会

### 1.2.1 行业背景
- 全国甲级建筑/规划设计院共约 5000 家，从业人员约 150 万（基于公开资料整理）
- 设计规范体系庞大：国家标准 + 行业标准 + 地方标准合计 2000+ 部
- 数字化转型加速：AIGC 浪潮下，设计院普遍探索 AI 提效工具

### 1.2.2 市场空白
**"规范权威性 × AI 智能化 × 可溯源"** 三者交集是当前市场空白。

## 1.3 用户痛点

### 痛点 1 · "查不到"
- 不记得规范号，关键词搜索定位不到具体条文
- 跨规范查询（国标 vs 北京地标差异）需要打开多个文件对照
- 不知道哪部规范现行有效

### 痛点 2 · "看不懂"
- 规范条文用词专业晦涩
- 不知道某条规定是强制还是推荐
- 多条文交叉，难以整合判断

### 痛点 3 · "不敢用"
- 通用 LLM 工具回答看起来合理，但无法验证
- 错用规范可能导致审图不通过
- 缺少权威背书的 AI 工具

## 1.4 项目目标

### ✅ 本项目解决
- 让规划师用自然语言快速查到准确的规范条文
- 提供精确到条文级的引用溯源，可点击跳转原文 PDF
- 明确区分强制性条文与推荐性条文
- 覆盖规划、建筑、景观、消防、结构 5 类核心规范
- 边界情况诚实告知"未查到"，绝不编造

### ❌ 本项目不解决
- 不替代设计师的专业判断
- 不提供具体项目的合规审批结论
- 不解读上传的设计图纸（V2 计划支持）
- 不覆盖造价、施工、设备选型等非规范类问题

# 第 6 章 · 核心交互流程

## 6.1 设计原则
- 每个流程都要画异常分支（单人项目最容易漏的）
- 状态机思维（每个页面有几个状态？怎么转换？）
- 零思考交互（用户不需要"想"下一步该做什么）

## 6.2 主流程（Happy Path）

```
用户打开网站 → P1 首页
   ↓
看到示例问句 + 输入框
   ↓
[A] 点击示例问句   或   [B] 手动输入
   ↓
跳转 P2 问答页，显示用户问题
   ↓
系统流式生成回答（TTFT ≤ 3s）
   ↓
完整回答（结论 + 引用 + 追问）
   ↓
[1] 点击引用卡片 → P3 查看原文
[2] 点击追问按钮 → 直接发起追问
[3] 复制回答 → 粘贴到工作文档
   ↓
任务完成
```

> 关键体验目标：从打开网站到看到答案 ≤ 10 秒（TTFT 3s + 阅读 7s）

## 6.3 5 类异常流程

### 异常 1 · 网络断开
- **触发**：发问时无网络 / 流式过程中断网
- **处理**：
  1. 输入框上方红色 banner："网络异常，请检查连接"
  2. 流式中断时保留已生成内容 + "重新生成"按钮
  3. 网络恢复后 banner 自动消失

### 异常 2 · API 超时
- **触发**：30 秒未收到 LLM 响应
- **处理**：
  1. 中断请求，显示"响应超时，请稍后重试"
  2. 提供"重新生成"按钮
  3. 后台记录超时事件

### 异常 3 · 检索无结果
- **触发**：未召回任何相关 chunks
- **处理**：
  1. 走"边界兜底"流程
  2. 明确告知"未在规范库中查询到相关内容"
  3. 提供 3 个相关方向 + 告知规范库覆盖范围

### 异常 4 · 输入异常
- **触发**：空输入 / 超长（>500 字）/ 含敏感词
- **处理**：
  1. 空输入：发送按钮 disabled
  2. 超长：提示"已超长度，请精简问题"
  3. 敏感词：拒绝发送，提示"问题包含不当内容"

### 异常 5 · PDF 加载失败
- **触发**：点击"查看原文"但 PDF 加载失败
- **处理**：
  1. P3 显示"原文加载失败"占位
  2. 提供"重新加载"+"返回上一页"按钮
  3. 显示规范名称纯文本（保底信息）

## 6.4 P2 问答页状态机

```
S0 空态（无对话历史）
  ↓ 用户输入并发送
S1 用户消息（显示用户问题）
  ↓ 触发检索 + LLM
S2 加载中（显示打字光标）
  ↓ 首字到达
S3 流式输出（逐字显示）
  ↓ 流结束
S4 完成（显示完整回答）
  ↓ 继续提问（回到 S1）

S5 异常态（超时 / 网络断 / 服务异常）
  ↓ 用户点击"重新生成" → 回到 S1
```

### 关键交互规则
- S2 → S3：首字必须 3s 内到达
- S3 中：用户可中断（"停止"按钮）
- S4 完成后：可复制、可追问、可看引用
- S5 异常：保留已生成内容 + 重试入口

## 6.5 必须明确的 12 个交互细节

| # | 细节 | 规则 |
|---|---|---|
| 1 | 发送方式 | Enter 发送 / Shift+Enter 换行 |
| 2 | 输入框最大字数 | 500 字，超出显示计数提示 |
| 3 | 流式输出速度 | 跟随 LLM 实际速度，最低 20 tokens/s |
| 4 | 用户能否中断流式 | 可以，提供"停止"按钮 |
| 5 | 引用卡片样式 | 横向（PC）/ 竖向（移动），强制性条文红色标签 |
| 6 | 引用点击行为 | 新标签页打开 |
| 7 | 复制内容范围 | 仅复制回答正文 |
| 8 | 历史保留范围 | MVP 仅本次会话（sessionStorage）|
| 9 | 页面刷新行为 | 提示"刷新会清空对话" + 二次确认 |
| 10 | 输入禁用规则 | 流式中：发送变"停止"，可输入但不可发送 |
| 11 | 移动端键盘弹起 | 输入区域上移 |
| 12 | 暗色模式 | MVP 不做 |

# 第 7 章 · 功能详细说明（11 个 MVP 模块）

## 7.1 模块 A1 · 智能问答

### 模块概述
基于规范库的智能问答能力，是产品的核心引擎。

### 触发条件
- P2 输入并发送
- P1 点击示例问句（自动跳 P2 + 自动发送）
- 点击追问按钮（自动填充并发送）

### 输入

| 字段 | 类型 | 必填 | 说明 |
|---|---|---|---|
| query | string | ✓ | 用户问题文本，1-500 字 |
| session_id | string | ✓ | 会话标识 |
| user_context | object | ✗ | 预留：用户角色等（MVP 可不传）|

### 处理逻辑
1. **输入校验**：长度、敏感词、空内容
2. **场景识别**：6 大场景分类
3. **检索召回**：向量检索 Top-K（K=5）相关 chunks
4. **重排过滤**：rerank 重排，过滤相关性 < 0.3
5. **生成回答**：query + chunks → LLM 流式生成
6. **后处理**：提取引用、识别强制性条文、生成追问

### 输出
```json
{
  "session_id": "abc123",
  "message_id": "msg_001",
  "scenario": "规范查找",
  "answer": "居住区配套幼儿园服务半径不应大于 300 米",
  "citations": [{
    "spec_name": "城市居住区规划设计标准",
    "spec_code": "GB 50180-2018",
    "clause": "表 5.0.3",
    "page": 14,
    "is_mandatory": true,
    "original_text": "幼儿园服务半径不宜大于 300m..."
  }],
  "follow_up_questions": ["小学服务半径是多少？", "完整配套清单？", "规模与班级要求？"]
}
```

### 异常处理
- 检索无结果 → 触发 A5 兜底
- LLM 调用失败 → "系统繁忙，请稍后重试" + 重试按钮
- 超时 (>30s) → 中断，提示超时
- 输入校验失败 → 输入框上方红色提示

### 验收标准
- 生成层 7 维度平均得分 ≥ 75 分
- TTFT P95 ≤ 3s
- 总响应时长 P95 ≤ 15s
- 评测集 250 条 query 全部能正常返回

### 依赖关系
- 依赖：LLM API、向量数据库、规范库
- 依赖模块：A2 / A5 / B1

## 7.2 模块 A2 · 引用溯源

### 处理逻辑
1. 引用提取：从 retrieved chunks 提取规范元数据
2. 去重合并：同一规范的多条文合并为一卡
3. 强制性识别：基于 is_mandatory 字段
4. 跳转链接：构造 `/spec/:specCode?clause=X&page=Y`
5. 原文摘引：保留 chunks 中的原文片段（≤ 50 字）

### 输出元素
每张引用卡片：规范全称 + 标准号 + 版本 + 具体条款 + 页码 + 强制性标签 + 跳转链接 + 原文摘引

### 验收标准
- "引用准确性"维度得分 ≥ 1.8（满分 2）
- 100% 有规范依据的回答都有引用卡片
- 强制性条文 100% 正确标识（一票否决）
- 元数据 4 项完整率 ≥ 95%

## 7.3 模块 A3 · 原文跳转

### 处理逻辑
1. 路由跳转：新标签页打开 `/spec/:specCode?clause=X&page=Y`
2. PDF 加载：基于 specCode 查找 PDF
3. 页码定位：使用 PDF.js 跳转到指定页

### 异常处理
- PDF 不存在 → "原文文件准备中"占位 + 返回按钮
- PDF 加载失败 → "加载失败"+ 重试按钮
- 页码越界 → 默认打开第 1 页 + 提示"未能定位"

### 验收标准
- PDF 加载时间 P95 ≤ 3s
- 95% 引用能正确跳转
- 异常情况都有兜底，不出现白屏

## 7.4 模块 A4 · 追问引导（MVP 简化版）

### 处理逻辑（MVP 静态版）
1. 场景匹配：基于场景类型从预设规则库
2. 规范关联：基于当前回答涉及的规范
3. 数量控制：返回 3 个不重复的追问

### 验收标准
- 100% 回答都有追问按钮
- 追问点击率 ≥ 15%（V2 提升至 30%）

## 7.5 模块 A5 · 边界兜底

### 触发条件（8 种子情境）
- 检索结果相关性都 < 0.3（查不到）
- 涉及已废止规范
- 多规范明确冲突
- 超出 5 类规范范围
- 闲聊
- 模糊提问（缺关键信息）
- 敏感问题（涉及规避审查）
- 涉及审批权限问题

### 处理逻辑
1. 子情境识别：基于相关性分数、关键词、意图分类器
2. 话术匹配：从话术库匹配对应模板
3. 方向生成：基于子情境生成 2-3 个引导方向
4. 能力声明：附加规范库覆盖范围说明

### 验收标准
- "兜底合规性"维度得分 ≥ 1.8（满分 2）
- 8 种子情境 100% 有对应话术模板
- 对抗样本 100% 不出现编造（一票否决）

## 7.6 模块 B1 · 流式输出

### 处理逻辑
1. 前端订阅 SSE 流

5. 可中断：发送按钮变"停止"

### 异常处理

- 超时无响应 → 30s 未收到首字则中断

### 验收标准
- TTFT P95 ≤ 3s
- 吐字速度 ≥ 20 tokens/s
- 用户可随时中断
- 中断后已生成内容不丢失

### 指标定义

| 指标 | 计算方式 |
|---|---|
| TTFT | 请求发出 → 首字到达 |
| 总响应时长 | 请求发出 → 流式结束 |
| 吐字速度 | 总 token 数 / 流式时长 |
| 错误率 | 错误请求数 / 总请求数 |

### 验收标准
- 100% query 都有性能记录
- 监控开销 < 5% CPU

| Claude 3.5 | 长文档理解强 | 国内访问不便 | ¥80/百万 tokens | ⭐⭐⭐ |
| 文心一言 | 国产可控 | 中文表现一般 | ¥40/百万 tokens | ⭐⭐⭐ |

### 最终决策：DeepSeek V3（主）+ 通义千问 Max（备）

**决策理由：**
- 单人作业预算有限，DeepSeek 价格是 GPT-4o 的 1/200
- DeepSeek V3 在中文专业领域评测中表现优秀
- 通义千问 Max 作为备份，避免单点故障

## G.3 向量库选型决策

### 选型矩阵

| 向量库 | 优势 | 劣势 | 部署复杂度 | MVP 推荐 |
|---|---|---|---|---|
| **Qdrant** | 性能优秀、过滤检索强、Docker 部署 | 资源占用中等 | 低 | ⭐⭐⭐⭐⭐ |
| Chroma | 极简单、Python 原生 | 大数据量性能差 | 极低 | ⭐⭐⭐⭐ |
| Milvus | 工业级性能 | 部署复杂 | 高 | ⭐⭐ |
| Pinecone | SaaS 免运维 | 收费、海外服务 | 极低 | ⭐⭐ |
| FAISS | 性能最强 | 无元数据过滤 | 中 | ⭐⭐⭐ |

### 最终决策：Qdrant

- 支持元数据过滤（按规范类型、版本年份）
- 性能 + 易用性平衡最佳
- 35 部规范量级（约 5000 chunks）Qdrant 完全够用

## G.4 关键算法决策

### G.4.1 分块策略

| 策略 | 说明 | 选择 |
|---|---|---|
| 固定长度 | 按字符数切分 | ✗ |
| 段落分块 | 按段落边界 | ✗ |
| **结构化分块** | 按"章/节/条"边界 | ✅ 主策略 |
| 滑动窗口 | 重叠分块 | 🔶 辅助使用 |

**本项目分块方案：**
- **主策略**：以"条"为基本单元
- **辅助**：表格独立成块（不可切散）；公式独立成块
- **滑窗补充**：相邻条款做 50% 重叠备份

### G.4.2 检索策略

| 阶段 | 策略 | 参数 |
|---|---|---|
| **粗排** | 向量相似度检索 | Top-20（BGE-M3 + cosine）|
| **过滤** | 元数据过滤 | 按规范类型/版本 |
| **精排** | Rerank cross-encoder | Top-5（BGE-Reranker-v2）|
| **截断** | 相关性阈值 | ≥ 0.3，低于则兜底 |

### G.4.3 Prompt 工程要点

| 要点 | 说明 |
|---|---|
| 角色设定 | "你是一位严谨的设计规范查询助手" |
| 强约束 | "只基于提供的规范片段回答，不得编造" |
| 格式约束 | "用词必须与原文一致，区分应/宜/可" |
| 输出格式 | 结构化输出，便于后处理提取引用 |
| 兜底约束 | "如片段不足以回答，明确告知" |
