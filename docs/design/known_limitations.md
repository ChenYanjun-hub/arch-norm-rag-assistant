# 已知限制清单 · MVP 阶段

> **作用域**：记录 chunker / embedder / retriever 等模块当前算法触达不到的边缘情况。
> 这些**不阻塞 MVP**，但 W4 评测阶段或上线前需要决定是否兜底处理。

---

## 一、Chunker 无法处理的 PDF（3 部，已知）

| 文件 | 根因 | 影响 | 建议处理 |
|---|---|---|---|
| `建标 109—2008《农村普通中小学校建设标准》.pdf` | 用**全角数字**（如 `表４３`、`６班２７０人`），现有正则 `\d` 不匹配 | 完全无法入库 | A. 增加全角数字正则支持；B. 接受不入库 |
| `建标192—2018号《中等职业学校建设标准》_可搜索.pdf` | OCR 后**表号字符错乱**（`表 ` → `&(!!`），章节号也是怪字符 | 完全无法入库 | 重做 OCR / 接受不入库 |
| `上海市"15分钟社区生活圈"行动工作导引》.pdf` | PDF 字体 **cmap 错乱**，pymupdf 提取的文本全是乱码字符（`╙⪓ꪫ顖䏗`） | 完全无法入库 | 字体修复（专业工具）/ 接受不入库 |

**MVP 决策**：3 部均**接受不入库**。理由：
- 它们都不是规划/建筑核心规范
- 用户访谈未提到对这 3 部的高频查询需求
- 修复成本（特殊 OCR 流程）远高于收益

**实现位置**：
- `JGJ39-2016 原版` 与上述 3 部，统一在 `backend/scripts/ingest.py` 的 `INGEST_EXCLUDE_FILES` / `INGEST_FILENAME_OVERRIDES` 中管理
- 解析失败时报错并写入 `_ingest_report.json` 的 failed/empty 列表

## 二、Chunker 对 OCR 错字的鲁棒性边界

试金石 GB 50180-2018 已暴露的 OCR 错字案例：

| 现象 | 例子 | 影响 |
|---|---|---|
| 条文号被错识 | `3.0.8` → `5.0.8`、`4.0.5` → `4.0.53` | 个别引用号错 |
| 章节标题被错识 | OCR 错字行被当成章节 | chapter 字段错乱但 chunk text 仍正确 |
| 字符模糊 | "宜居" → "宜适"、"4.0.5" → "40.5" | 检索仍能召回（BGE-M3 容错） |

**MVP 决策**：接受现状。W4 评测时统计错率，> 5% 才单独修。

## 三、Embedder 性能瓶颈

| 项 | 值 | 说明 |
|---|---|---|
| 单部 PDF embed 耗时 | 5-35s（CPU）| BGE-M3 + sentence-transformers on M-series CPU |
| 全量 42 部 embed | ~8-10 分钟 | 一次性，可接受 |
| query 端 embed 耗时 | < 1s | 在线请求 OK |

**优化路线**：上线前若 query QPS > 5，考虑：
- 起一个 BGE-M3 常驻服务（避免每次 import 加载）
- 切 GPU 推理（成本 ↑）
- 改 BGE-small-zh（dim=512，质量略降但快 3-5×）

## 四、Retriever 模式切换待办

当前用 **Qdrant 本地文件嵌入模式**（zero ops）。上线前需：

| 切换前 | 切换后 |
|---|---|
| `QDRANT_URL=` 空 | `QDRANT_URL=http://qdrant:6333` |
| `QdrantClient(path=...)` | `QdrantClient(url=...)` |
| 数据在 `data/qdrant_local/` | 数据在容器 volume |

切换成本：改 env 一行 + 起 Docker，retriever 代码零修改。

---

## 五、当前不做（W1 阶段）

- 跨章节关联（如「5.0.3 引用 4.2.1」）
- 图片/示意图 OCR
- 公式 LaTeX 化
- 中英规范并存（仅中文）
- 多版本规范并存（同标准号不同年份）
- 实时增量入库（修改 PDF 后自动 re-ingest）

这些都是 V2/V3 范围，PRD 已明确不在 MVP。
